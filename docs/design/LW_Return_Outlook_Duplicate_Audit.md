# 帰還見通し・候補評価の重複調査

2026-11-11。必要な探索・判断を減らすのではなく、同じ材料に対する重複計算を調べた。通常実装の変更なし。

## 実測で確認した重複

`mb_return_outlook!` は探索ループの末尾で待ち列をソートし、次の先頭でも同じキー `(cost,node,path_key)` でソートする。訪問済みノードの取り出しでcontinueする場合も、残った列の順序は崩れない。

39・41日目の直前に当たる38・40日目保存状態の4個体ずつ、計8状態で、キャッシュ期限を診断用コピーだけ0にして再構築を1回ずつ実行。計測関数は元と同じソートを行い、その直前の整列状態を追加確認した。元関数との返却辞書の一致を8件確認。

- ループ先頭ソート：4,009回。**全4,009回が既に整列済み**。
- 先頭ソートに渡った列長の累計：918,080要素。比較回数やソートによる移動回数ではない。
- 末尾ソート：2,048回。そのうち1,037回が既に整列済み。
- 各状態で展開済みノードは上限256。先頭ループは451〜544回で、訪問済みノードの取り出しも含む。

これは8回の再構築の局所検査であり、2日間全体の重複回数ではない。整列済みソートは一般に未整列より安く、ソート回数の削減率を実時間の削減率と見なさない。`issorted`の追加自体も診断負荷であり、その時間を性能値として使わない。

通常経路探索 `mb_search` にも同じ先頭・末尾ソート構造がある（ソース確認のみ）。安全な改善候補は、初期列の整列を保証した上で、その後の列変更に応じて必要な整列だけを残すこと。探索順、同点順、列の上限切り詰めは維持する。キューの重複ノード除去は経路選択や上限への影響があり、単純な整列省略と混ぜない。

## その他の候補と、既存の再利用

- `mb_parent_candidates!` は各候補で見積もり・予算辞書を作る。search/approachでは同じ目的・距離・モデルなら共通結果になる余地がある。実際の候補の重複率は未計測。候補ごとに後からplanning/return_homeを付加するため、可変辞書の単純共有は不可。
- `mb_project_return!` は候補ごとに同じ到達ノードの帰路を検証する場合がある。呼出し内で同じキーの結果を再利用する余地はあるが、重複頻度は未計測。長期キャッシュは辺削除やhome情報更新の無効化が必要。
- 帰還見通しには既に64秒キャッシュがある。候補ごとにグラフ全体を再構築しているわけではない。
- `mb_simulate!` は接続表を一度作り複数照合先に渡す。既に候補間で再利用している。
- `mb_parent_survival!` はモデル内forecastをキャッシュし、学習更新時に無効化する。候補ごとに生存推定を全再計算しているわけではない。
