## 0. 決定事項と最初の着手点

既存LWのJulia移植を優先し、汎用層／専用層の大規模整理は移植完了後に行う。本計画は、待機中に挙げた最適化候補を、実装・比較・採否判定へ渡せる形にしたものである。[U1–U4]

進行中の受入用30日実行がある場合、その対象コード・設定・成果物を固定し、最適化変更を混ぜない。完了、失敗、タイムアウトのいずれも結果として保存してから、別の比較基準を作る。**この文書を渡しただけで、Actionsの取消・再実行・新しい長期ジョブの起動を許可したことにはしない。**

最初は **M00（測定の足場）→ J01（遅延生成など）・C01（地面解析の共有）**。CPUプロファイルを見て **C02（Skylineの水平交差再利用）** を優先し、割当側では **J02（BodyDelta）→ J03（移動観測・候補の型）** を調べる。すべてを一度に実装しない。

「最も大きく効きそうな候補」と「低リスクで始めやすい候補」は別である。現時点の静的な第一候補はSkylineだが、全体時間への寄与率は未測定。小さな書換えから得る利益を確認しつつ、実測で順序を変えてよい。

## 1. 目的・範囲・非目標

### 1.1 目的

JuliaネイティブLWの一回の生活実験を短くし、累積割当・ピークメモリ・検証費用を抑える。主指標は、同じ実行条件でのシミュレーション時間と、World生成から保存までの実時間である。局所関数だけが速くなったことを、LW全体の改善と呼ばない。

同時に、観測に基づく選択、方法と親目的の区別、経験の後続利用、身体・資源の更新という、現在評価している生活の働きを残す。全員の帰還、採取増加、Sleep完了数の増加を、最適化の成功条件として強制しない。

### 1.2 対象となる実行経路

```text
lw_integrated/native.jl
    → run_integrated()
    → lw_day()
    → 観測・候補評価・身体更新・経験保持・Sleep
    → result / summary / manifest の保存
```

既存の共通生活ループへ変更を接続する。マイクロベンチ用の小さな関数呼出しは作ってよいが、機能ごとに別の生活シミュレータを増設しない。[R01, R03]

### 1.3 今回の非目標

汎用RDL Kernelや独自DSLの完成、全ファイルの再配置、GPU化、共有Worldの個体更新の並列化、未実装の認知機能追加を、最適化の前提にしない。現行コードの動作を変える大きな学習則や目的管理の追加も、この計画へ混在させない。

`@fastmath`、Float32化、観測頻度低下、ρ変更、経験の追加削減などは、後述のA区分で別に扱う。計算量削減と意味変更を、同じ「高速化」の一語で処理しない。

### 2.3 ソース確認と静的推定

| 対象 | 確認した構造 | 現時点で言えること |
|---|---|---|
| Skyline | 仰角3段ごとに同じ水平レイと物体の交差を再計算 | 再利用候補。CPU時間の最大部分かは未確定 |
| 地面模様 | `record_ground_patterns!`と`update_ground!`が同じ観測を解析 | 一つの観測に対する重複解析を除ける候補 |
| 身体・移動 | `Body`は型付き、`delta`は固定四項目の辞書、観測行は`Any[]` | データ表現を軽くする候補。型付きBodyまで捨てない |
| 方法選択 | 読み取り選択を各寄与段階で反復し、その都度ソート | 一回の選択を軽くできる候補。比較の意味は残す |
| Sleep | 候補ごとに保持記録を走査し、入れ子contextを比較 | 索引化候補。索引維持費も必要 |
| 管理状態 | `get!`等の既定値に辞書・配列・MethodNodeを直接生成 | 遅延生成の候補。除去可能な割当量は実測する |
| 内部キー | selection trailでJSON文字列を候補ごとに作る | 型付きキーの候補。同一性の変更リスクあり |

Skylineの元ループでは、端のサブレイを除き、1回につき `3 × (11×3 + 2×2) = 111` の方向・仰角組を評価する。95物体、155,520観測なら、ソース上の `ray_hit` 呼出しは `111 × 95 × 155,520 = 1,639,958,400` 回となる。[R05, D01–D02]

これは**ソースの呼出し回数の計算**であり、実行時プロファイルでも、全体速度の予測でもない。仰角をまたぐ距離再利用で、この部分の水平交差回数を約1/3にする案はあるが、LW全体が3倍速くなるとは言えない。休息比率も、削減可能なCPU時間の割合ではない。

## 3. 実験を三つの区分に分ける

| 区分 | 変更するもの | 比較の基本 |
|---|---|---|
| **P：意味を維持する計算・表現変更** | 重複計算、割当、データ構造、探索手順 | 同じ有限入力で観測内容・状態遷移・選択が維持されたかを診断する |
| **O：観察用の保存・検査費用の変更** | 外部ログ、診断出力、保存形式 | 失う可観測性を明示。判断や学習に使う情報を誤って削らない |
| **A：近似・仕様調整** | 精度、ρ、周期、候補、記憶保持など | 変わる範囲を先に宣言し、関係応答・実行成立・費用で評価する |

P区分では、結果一致を「意味を変えていない」という仮説の強い診断に使う。JSONの順番・型表現・新診断項目が違うだけなら、明示した正規化を行ってよい。ただし不一致を無言で無視しない。

一致を維持するための巨大なコピーや互換層が重くなるなら、**Pのまま偽装せずO/Aへ分類を変え、失うものを明記して再評価する**。旧Python・旧Juliaとの完全一致は、今後すべての採用に課す絶対条件ではない。[R00, U1]

どの区分でも、未観測情報をこっそり選択へ流す、資源を二重生成する、出典のない体験を作る、失敗や未実行を成功と表示するといった事故は許容しない。規則自体を意図的に変える場合は、対応する実験契約を別に定める。

## 5. 測定計画 M00

### 5.1 固定して記録するもの

コードSHAとdirty差分hash、specの元bytesとSHA-256、Julia版・Project/Manifestのhash、OS・CPU・メモリ・runner種別、Julia/BLASのスレッド数、全機能フラグ、記録モード、乱数条件、測定対象範囲を保存する。

基準レポートはJulia 1.13.1を記録している。新しい測定でも使用した版を記録し、言語版変更と実装最適化を一回の比較に混ぜない。版の更新が必要なら、その比較を別に残す。[R01, R02]

### 5.2 時間とメモリを分ける

| 指標 | 測り方・読み方 |
|---|---|
| 起動から結果保存まで | 新規プロセスの実時間。読み込み・コンパイル・生成・実行・保存を含む |
| 準備後の生活計算 | 同じ準備手順でコンパイルを済ませ、初期状態を新しく作って実行 |
| 局所関数 | 戻り値を消費し、最適化で仕事が消えない条件で反復 |
| 累積割当／操作 | 割当bytesと実際の完了操作数を報告。保持RAMではない |
| GC時間 | 実行時間と併記。CPU原因の全内訳とは扱わない |
| ピークRSS | 比較ごとに新規プロセス。`Sys.maxrss()`の同一プロセスreplay値を独立ピークとしない |
| 出力生成・書込み | 計算時間とは別に測る。計算側から出力側へ費用を移しただけでないか確認 |
| コンパイル負担 | 初回／準備後の両方を示す。型の種類が増えた影響を隠さない |

中央値・最小／最大または分位範囲・生標本を残す。固定倍率を合格条件にしない。初期案として短い測定は5標本程度から始め、揺れが大きければ追加する。長い3日・30日実行へ同じ反復数を機械的に適用しない。

状態更新関数は、同じ状態を何度も使うと測定中に仕事の内容が変わる。各標本の状態を復元し、復元費用を計時内／外のどちらに置いたかを記録する。通常実行で必要なコピーを、ベンチだけ計時外へ逃がさない。

### 5.3 代表区間

初期の観測・探索、学習後の候補選択、危険・身体負荷、夜の休息とSleep完了、履歴が増えた後の処理を候補とする。すべてが一つの自然Worldで出る保証はない。出なかった境界は既存の短い専用試験で補い、自然実行の成果とは分ける。

現行`native.jl`には任意tickの完全な個体状態再開があるとは仮定しない。保存specから目的区間まで同じ生活を進め、その区間だけ計時する軽いフックを提案する。環境だけのcheckpointを個体の記憶・Hまで復元するものと誤認しない。完全再開基盤の新設を初手の前提にはしない。

### 5.4 調査用ツール

CPUは`Profile`、割当は`Profile.Allocs`、型の伝播は`@code_warntype`等で調べる。プロファイル取得と最終速度測定は分ける。[L04–L05]

割当プロファイルは短区間の低いサンプル率から始める。全件記録は測定自体を重くする。サンプルは割当回数に対する抽出であり、そのままCPU時間比や全割当bytesの厳密な内訳としない。`@code_warntype`の表示だけでボトルネックを確定せず、実際の型・呼出し頻度・割当と合わせる。

計測フックは観測回数、時刻、作用順、乱数消費、Hや利用実績を変えない。大きな引数の表示や毎tickのログ出力を、計測のために追加しない。

## 6. 小変更と重複削減の実験

### J01：必要な場合だけ既定値を作る

**根拠。** `BasicLoop`の方法登録、Sleep管理状態、selection trailに、生成式をそのまま`get!`等の既定引数へ渡す箇所がある。`get! do`はキーがない場合だけ生成を呼ぶ形である。[R06, R10, R12, L01]

```julia
# 変更案。関数全体の実装・性能は未検証。
node = get!(s.methods, name) do
    MethodNode(0, s.threshold, 0)
end
```

入れ子の`D()`、`Int[]`、`Any[]`にも適用候補がある。ただしコンパイラが既に除去する生成は改善しないので、命中／未命中を分けて測る。生成式に副作用がある場合、遅延化は意味変更になり得るため個別に確認する。

`merge(copy(selected), D(...))`は、一度の`copy`後に必要項目を代入する形を試す。読み取りだけの`reverse(history)`は、走査中の変更がない場合に`Iterators.reverse(history)`を試す。[R06, R11, L02]

**検査。** 初回登録、既存登録、個体間の独立性、例外時の未更新を確認する。空の可変辞書を全個体で共有する「最適化」はしない。Sleep開始時の短い反転は頻度が低いので、全体利益を過大評価しない。

### C01：地面模様を一つの観測につき一回だけ解析する

**根拠。** `record_ground_patterns!`と`update_ground!`が同じ観測に`ground_patterns`を使う。[R07]

一度得たpatternを記録側と連続性更新側へ渡す。元の観測取得回数、source、capture時刻、部分観測の扱いは変えない。共有patternを読み取り専用とし、片方が書き換えるなら、その小さな可変部分だけを分ける。

**検査。** 15サンプルの全草地、混在、遮蔽、未取得、帯候補、曖昧対応、連続性消失を通す。関数呼出し回数の半減と、全体速度の改善を別に記録する。

### C02：Skylineの水平交差を仰角間で再利用する

**根拠。** `skyline_fan`は仰角0／15／30度で水平交差を反復する。水平レイと物体の距離を先に計算し、仰角ごとの高さ判定へ再利用する。[R05]

第一段階は**同一観測の内部だけ**で共有する。静的物体の中心・半径・高さ・色を一度型付きで用意する案は、別コミットまたは別標本として比較する。水平ランドマークの中心レイを共有するのは、最初のSkyline比較後に追加する。

**重要な境界。** 全物体から水平で最も近い一個だけを先に選び、それを高仰角にも使ってはいけない。近い低物体が高さ条件を満たさず、背後の高物体が見える場合がある。仰角ごとに条件を満たす最短距離を選べる情報を残す。

サブレイの±90度端、48の観測距離、物体内からのray、接線、同距離、色フィルタ、range band境界、低障害物と視覚遮蔽の区別、元の`d < best`による同順位順を検査する。三角関数の式変形や丸め変更は同時に入れない。

**測定。** `ray_hit`呼出し回数、Skyline単体、観測一式、短い生活区間を測る。仰角間共有の局所効果から、LW全体の倍率を推定しない。空間索引はさらに後の候補とし、小さな95物体で本当に必要か測る。

### C03：全ソートから、同じ順位規則の最良候補選択へ

**根拠。** `method_choice`は`first(sort(...))`を使い、複数の寄与段階から呼ばれる。BasicLoop全体のコピーを使う診断は既に読み取り選択へ変わっているので、旧問題を再発見したことにしない。[R06, R09]

現行の通常順位と「全方法が未解消なら最も長く未試行の方法を再検討する」順位を、そのまま比較キーにして走査する。候補数は少ない場合もあるので、計算量の理屈だけで採用しない。

**検査。** 空集合、新方法、全方法未解消、H上限、同score、同最終試行時刻、文字列による最終同順位規則、候補順の違い、非有限score拒否を含める。キーが完全同一なら、元ソートの安定な選択順を保つ。

採取→Sleep→身体→経験束→trailの途中比較は、寄与の帰属や利用実績にも使われる。削るより先に一回の選択を軽くする。同じ候補版に対する結果を再利用する場合は、どの寄与が候補を更新したかを追い、古い選択を返さない。

## 7. Julia向けの表現・検索・再利用の実験

### J02：身体の数値戻り値を小さな型付きレコードへ

**根拠。** 現在の`Body`は四つの`Float64`を持つ構造体だが、`step()`の変化量は固定四項目の辞書で返される。この辞書の数値型が揃っている点と、外側の観測辞書・`Any[]`が型を曖昧にする点を混同しない。[R08]

```julia
# 内部表現の候補。既存のstep()への適用は未実装。
struct BodyDelta
    burst::Float64
    strain::Float64
    reserve::Float64
    damage::Float64
end
```

同じ項目の`NamedTuple`も対照候補とする。固定レコードを返し、観測計算側では`.reserve`等で読む。保存や旧インターフェースが必要な境目でだけ辞書へ変換する。戻り値を直ちに毎回辞書へ変換し直して、費用を移すだけの試行にしない。

**検査。** 全身体操作、瞬発力・strain・reserve・damageの境界、荷重5/6と高さ0.4、blockedとbody-limitedの区別、地面抵抗、静止・食事・休息を確認する。型の変更と身体式・Float32化を同時に行わない。

**測定。** `step()`単独、五方向の移動観測、生活区間の三段階で調べる。不変structなら必ずゼロ割当になる、とは仮定しない。[L03]

### J03：受け渡し経路の具体型を揃える

**根拠。** `rows=Any[]`、`surface=Any[]`、候補辞書、`BasicLoop.trial::Any`／`receipt::Any`、`food=Any[...]`が残る。`const D=Dict{String,Any}`を再宣言しても内部値の型は明確にならない。[R06, R08–R09, R14]

初回は **Body → BodyDelta → 移動観測行 → 候補評価** の狭い経路を選ぶ。固定項目に`struct`／`NamedTuple`、固定五方向には`NTuple{5,T}`または`Vector{T}`、試行・結果には具体型と`Union{Nothing,T}`を検討する。[L03]

不明なcostを0で埋めない。未知・blocked・unavailableなどは、現在必要な区別を型付き状態として残す。全引数へ型注釈を付けるだけの作業や、`Vector{AbstractCandidate}`を作って終える作業を成果にしない。

用途別の補助情報を持つ候補は、一律に巨大なstructへ押し込まず、測定対象の固定項目と周辺の補助payloadを分ける案を試す。個体ID、時刻、M_Bの識別子、刻々変わるρを型パラメータにしない。変化する関係網はデータとして保ち、処理形式だけを型で明確にする。

**検査。** 呼出し側の全検索項目、未存在項目、候補の同順位順、内部値と保存値の対応を確認する。構文の短さではなく、型推論・割当・コンパイル費用を測る。

### J04：作業バッファと保持する経験を分ける

現在の観測・候補・contextには、毎tickの配列生成と、履歴登録時の複製がある。五方向サンプルや候補作業領域を再利用する一方、夜まで保持する経験へ意図せず上書きが波及しないよう所有を分ける。[R08–R11]

```text
現在tickの作業領域       次tickで上書き可
採用した観測・経験値     必要な内容・出典を独立保持
明示snapshot             宣言した範囲だけ独立した写し
World・H・現在試行       所有担当がその場更新してよい
```

不変の外側structに可変配列を入れただけでは、深い内容まで不変にならない。共有するなら内部まで不変の値、または実行中に書き換えない所有契約が必要になる。全Worldや全履歴の不変化は要求しない。

32／64件等の有限ログについて、実測で効果があればリングバッファを検討する。見た目の`popfirst!`だけで主要費用と断定せず、保持順序、最新N件、容量超過カウンタ、凍結後の独立性を確認する。

**検査。** 個体Aの作業領域更新でBが変わらないこと、夜の凍結後に昼の作業領域を変更しても凍結経験が変わらないこと、同tickに全個体が選択してから逐次実行する現在の順序を崩さないことを確認する。

### C04：候補ごとの履歴走査を索引へ

**根拠。** `project_sleep_actions!`は候補ごとに最大192件の記録を走査し、context・action・direction・休眠状態を調べる。経験束も現在文脈と各sourceを照合する。[R13]

まず、文脈の比較を一度にまとめる小さな索引から始める。候補は `(owner, context, action, direction)` 等の現在の同値条件を保持し、該当sourceと成功／blocked件数を参照する。phaseは現在の適用・復帰規則で使う場所に限って含め、性能のために適用条件を変えない。

登録、失効、休眠、復帰、容量超過、source競合で索引を更新する。検索を速くしても、そのため毎tick全記録をhash化・複製するなら、管理費込みで比較する。小さい記録件数では線形走査が有利な可能性も残す。

**検査。** 同じsourceを複数の独立証拠として数えないこと、別sourceの同一結果は正当に残ること、利用機会・実使用・休眠判定が元と一致すること、欠測contextと形成直後の利用禁止、復帰上限を確認する。単に最終選択が一致するだけでは、利用履歴の一致を確認したことにならない。

### C05：静的な幾何のキャッシュ

C02が有効なら、位置・向きが変わらない場合に、静的地形の幾何計算を再利用する。キー候補は位置、向き、センサ設定、対象幾何のrevision。revision取得のために毎tick全地形をhash化する方式は避ける。

観測ID・時刻・取得イベント・学習への受付は現在tickのものを作る。再利用するのは同じ条件から得られる幾何結果であり、過去の記憶を現在観測と偽ることではない。[R05, R08–R09]

| 変化 | 原則 |
|---|---|
| 位置・向き・サンプル数・距離範囲 | 該当センサのキャッシュを失効 |
| 観測対象の追加・削除・移動・高さ変更 | 該当する静的幾何のrevisionを更新 |
| 身体・荷重・地面抵抗 | 物理的交差だけ再利用可能でも、身体可否・costは再評価 |
| 危険・他個体・地上荷物・在庫 | 動的な対象。静止した本人だけを根拠に再利用しない |
| 摩耗・回復・時刻に依存する外観 | 回復による分類境界も追う。地面模様を単純に静的扱いしない |

歩行の観測範囲と実行範囲、走行距離、登攀の着地条件を同じキャッシュへ無条件にまとめない。休息中も危険や身体・Sleepの必要な更新を残す。

**検査。** 長い静止中の危険接近、資源再生、他者の採取／荷下ろし、地面回復、方向転換、センサ設定変更を含む。キャッシュ管理費込みで、命中／失効の多いケースの両方を測る。

### J05：内部キーをJSON文字列から分離する

`trail_key`は候補ごとにJSON文字列を作る。[R12] 文脈と行動の小さな不変tuple／structを内部キーにし、保存時だけ文字列へ変換する案を試す。

キーに可変配列をそのまま使い、挿入後に内容を変えない。元のJSON表現とJuliaの`==`／`isequal`／hashの違い、整数と浮動小数、`nothing`、符号付きゼロ、配列とtuple、並び順、ownerと目的の識別を調べる。ハッシュ値だけをIDにして衝突を無視しない。

actionのenum化や内部方向IDの整数化も候補だが、method名による同順位規則や外部sourceを維持する。動的M_Bの識別子を無制限に新しい型・Symbolへ変えることは初回に行わない。

**検査。** 旧キーと新キーの対応表、読込み／保存、replay、別個体・別目的・別contextの分離を確認する。キーの統合・丸めを意図するならA区分へ移す。

### J06：準備処理と具体型の反復計算を分ける

JSON入力の検査・変換・条件分岐を準備処理へ寄せ、具体型を引数として受ける計算関数へ渡す境界を検討する。これはfunction barrierの利用案であり、関数を短くすれば自動的に速くなるという意味ではない。[R09, L06]

最初は観測一式や候補選択など一経路に限定する。型付きの地形・callableを受ける関数を作り、実行時の分岐が必要な値はデータのまま保持する。何十個ものBoolフラグの全組合せを`Val`や型へ持ち上げない。

抵抗関数等のクロージャも一律廃止しない。捕捉変数のboxing、型不明のフィールド、特殊化されない転送呼出しが実測で問題なら、局所変数・具体型・引数の受渡し方を変えて比較する。現コードに`Core.Box`が必ず出ているとは確認していない。

**検査。** 機能フラグの有効／無効、callableの種類変更、初回コンパイル費、同じ関数を複数Worldで使った結果を確認する。汎用Kernel／専用LWの再編は別工程として残す。

### O01：診断のための仕事を分離する

通常計算、学習に必要な利用実績、外部観察だけの診断を分類する。ログの要約・間引きは提案できるが、Sleepの`uses`や`opportunities`、選択差から更新される休眠・信用などは単なるログではない。[R10, R12–R13]

小さな変更の第一候補は、更新後に捨てるだけの出力レコードや、後続処理が参照しない集計の作成費である。診断のサンプリングをする場合は何が未観測になったかを明示し、全件診断と同じ証拠を得たと報告しない。

現在の計算時間とJSON生成時間を別に測る。結果表示だけを小さくして、シミュレーション本体が速くなったとしない。必要な実使用判定を維持したまま、外部への記録だけを減らせるかを確認する。

### A01：近似を伴う実験は別契約にする

P区分が十分でない場合や、近似の方が費用と働きの釣合いに優れる場合、ρ、周期、数値精度、候補制限、文脈の統合、保持量変更を試してよい。P区分をすべて完遂してからでなければ試せない、という条件は置かない。[R00]

ただし、変更する問いを先に分ける。

- B：何を観測・操作対象とするか。
- ρ：その境界内で何をどこまで区別するか。
- 更新周期：いつ取得・比較・更新するか。
- キャッシュ：同じ計算結果をどこまで再利用するか。

これらは同義ではない。[T01–T03] 例えば休息中にセンサ頻度を下げるなら、危険への反応、食事／通信の割込み、Sleep経験の形成時刻への影響を評価する。Float32化や`@fastmath`を使うなら、接触・荷重・閾値・同順位選択の変化を測る。

当初のPバッチでは`@inbounds`・`@simd`等を一括追加しない。境界検査を省くなら添字の正当性を保証できる局所へ限定する。SIMDや演算順の変更は共有状態更新と分け、浮動小数結果が変わる可能性を検査する。[L06–L07]

## 8. 共通の検証境界

次の表は毎変更で全件実行する指示ではない。対象の変更が触れる行と、代表的な統合を選ぶ。

| 境界 | 確認内容 |
|---|---|
| 個体と出典 | owner、source、operation、時刻が対応し、他個体の経験が混ざらない |
| 現在観測 | completeは有限センサ内の完全性。未観測を不存在や0へ補完しない |
| 身体・接触 | 選択時の可否と実行時の再検査、荷重・地面・着地点の区別 |
| 資源収支 | 地上／携行／個人・共有備蓄／消費／補充を含む保存則 |
| 親目的と方法 | 荷下ろし成功で帰還を解除しない。運動成功だけで採取達成としない |
| E・H・θ | 現行の比較条件・更新順を、表現変更のついでに変えない。局所近似をcanonical T1と称さない |
| 経験保持 | 作業領域の更新が凍結経験へ波及しない。忘却・要約は別途宣言できる |
| 利用ライフサイクル | 形成直後の適用、重複受付、休眠／復帰、source重複、容量を検査 |
| 確率・順序 | 同じ乱数条件とtie-break。全員観測→全員選択→逐次作用の順序を保持 |
| 比較可能性 | 観測不能・未実行・不足材料を失敗や成功へ変換しない |

T0 SPECのEは、同じ更新前M_Bが形成する予測と後続解釈の比較に関する定義である。GameAIの個別カウンタや局所方法Hをそれと同一視せず、現在宣言している実装範囲を維持する。本計画の実装選別はGameAI側のもので、T0/T1の再定義ではない。[T01–T02]

## 9. 検証の段階と実施順

### 段階0：基準保存

受入用の結果・ソース・設定を固定し、30日結果が新たに得られたら旧3日値と別に保存する。失敗した基準を「成功したベースライン」に直さない。実装の正しさの問題と性能の問題を区別する。

### 段階1：単一変更の局所検査

一つの仮説に対して変更前／候補を測る。例えばJ01なら辞書の命中・未命中、C02ならSkyline境界fixture、J02なら身体一式。小さな仮説のたびに30日を実行しない。

### 段階2：代表区間・短い共通生活

同じ保存specから、同じコード経路で短い生活を実行する。少なくとも変更が働く機会を含める。局所の数値が良くても、この段階で全体が遅くなったりコンパイルが過大なら採用を保留する。

### 段階3：採用候補の組合せと3日比較

個別改善を統合し、2 seedの3日構成で測定する。単独の倍率を掛け算せず、合成後を測り直す。同じ箇所を別の案で最適化した場合、利益は重複し得る。

P区分では、保存出力の構造比較に加え、変更した局所観測／候補／履歴の比較を行う。終端の食料収支だけで同値と判断しない。一方、全観測の永久保存を新たな要件にはせず、差が出た区間に絞って詳細記録を取る。

### 段階4：長期影響がある採用候補だけ30日へ

キャッシュ容量、履歴索引、休眠更新、メモリ増加など長期性を問う変更では、主要バッチが揃った時点で30日・複数seedの確認を行う。純粋な小変更にも毎回この段階を強制しない。

初回とreplayは、決定性診断として有用だが、replayの必要範囲・回数も検証費用として扱う。許可なく既存の受入試験を取消・軽量化しない。将来の試験契約を変更する場合は、何を確認しなくなるかを明示する。

## 10. 採用・停止・再分類の基準

| 判定 | 条件 |
|---|---|
| **採用候補** | 対象の意味・関係応答を確認し、実使用条件で時間またはメモリ費用の改善がばらつきを超えて認められる |
| **局所改善のみ** | マイクロベンチは改善したが生活全体では効果未確認。結果は残し、複雑化に見合うか判断 |
| **割当改善のみ** | 割当は減ったが速度は変わらない。RSS・長期安定性等の価値を別に検討し、高速化とは呼ばない |
| **未判定** | 標本不足、効果が測定揺れ内、当該機能が使われない、比較条件不一致 |
| **再分類** | 予想外または意図した挙動差がある。原因と損失を示し、O/Aとして改めて評価 |
| **不採用／差戻し** | 意図しない情報漏れ・出典破損・資源破綻、費用増、保守負担に見合う利点なし |

速度倍率や削減率の一律ノルマは置かない。1 seedだけ速い場合はもう一方の退行を隠さない。初回だけ悪化し準備後だけ改善する場合、実際の「一回の実験」の時間と釣り合うかを判定する。

**停止すべきなのは、原因不明の実行破綻や検証条件の混同であり、最適化の余地がまだ残っていることではない。** 改善の小さい部分を追い続けて既存LWの完成を遅らせない。

## 11. 性能解釈の落とし穴

候補数・入力規模・機能フラグ・記録モードを減らした結果は、元と同じ処理の高速化ではない。A/Oとしては評価できるが、比較の名称を変える。

動くWorldの経路が変わった後は、処理機会、採取量、補充量、履歴数も変わる。「備蓄が増えた」「操作回数が少なくなった」を、それだけで実装速度の改善としない。局所的な同一状態比較と、全経路の生活結果を別に残す。

Juliaはマクロを加えたり、記法を短くしたりするだけで速くなるとは限らない。既に型付きの部分は維持し、実測で型不明・割当・繰返しの多い部分を狙う。型注釈の数、削除行数、導入した仕組みの大きさを成果指標にしない。

観測結果の共有、作業バッファ、内部キーの変更は、処理の副作用や所有まで含めて評価する。速い新関数の外で旧形式へ毎回全変換しているなら、全体費用にはその変換も含める。
