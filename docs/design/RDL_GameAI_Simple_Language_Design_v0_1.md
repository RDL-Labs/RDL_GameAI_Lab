## 1 目的と今回の決定

生活の中で使える少数の語句を初期教育として与え、個体が対象の名前を覚え、相手へ要求し、返答や実際の結果を経験できるようにする。その通信経路を、プレイヤーが「しゃべる神の像」として参加する入口にも使う。

初版は、既存の行動と結び付く言葉から始める。初期の語彙・文型・教育内容は設定してよい。チュートリアルを終えて基本語彙を覚えた状態を、生活の開始条件にできる。ゼロからの語彙・文法の発生は、初版の完了条件に含めない。

### 会話で確認した方針

- 表現には、ひらがななど人が発音できる文字列を使う。
- 音声波形や音場は計算せず、近距離で届く発話イベントとして扱う。
- 今ある要求・譲渡・拒否などに、対応する語句を与える。
- 対象の呼び名は「これ、なに？」「これは〈名前〉です」の教示で追加できるようにする。
- 初期教育で一通り教えた状態を用意してよい。
- 神の像からの言葉も、個体が受信し、解釈する入力として扱う。
- 日本語の表記・文型と、個体の関係記憶・行動処理を分け、別の表現設定を載せられるようにする。

本案で追加する具体的な設計判断は、初版を食料の名称と援助に絞ること、個体別の小さな言語状態を置くこと、段階A〜Cで接続を確認することである。数量交渉、一般会話、約束、自由な文法獲得、音響的な聞き間違いは後続の拡張とする。

### 初版で確認する一連の流れ

**教示または初期設定で「どんぐり」を知る → 「どんぐり、ちょうだい」と発する → 相手が自分の語彙で解釈する → 渡すか断るかを選ぶ → 選んだ現物を移す → 双方が自分の結果を記録する。**

話し相手が増えたときに、誰がどの呼び名を知り、どの経験を通して使うようになったかを追えることを重視する。

## 2 現行実装との関係

以下は調査基準コミットで確認した実装上の事実である。

| 現行の土台 | 今回の接続と追加 |
|---|---|
| communicate! は request / give / refuse / reach / warn 等を扱う | 任意の表現を届け、受信者側で解釈する入口を追加する |
| give は在庫数を実際に移し、成立時に given を通知する | 「どうぞ」という発話と物理的な譲渡結果を区別する |
| 相手・状況に応じた援助の応答選択と社会関係MBがある | 言語から得た本人側の解釈を、その選択へ接続する |
| social_mb_context は許可された数値特徴を受け取る | 任意文字列を既存の数値contextへ直接投入せず、語彙状態を分ける |
| 現行 request に要求食材種はなく、援助の現物選択は先頭の食材を中心に行う | 名前付き要求では、解釈した対象から実際に渡す食材を選ぶ処理が必要 |
| food_give! は指定した索引の食材を、品質・期限を保って移せる | 選択した索引をcargo、food在庫、receiptに一貫して反映する |
| 日末チェックポイントは保存変数、ソース、Julia版、入力identityを検査する | 語彙・未決会話・処理済みID等を保存対象に含める |
| 会話一般とプレイヤーの神像は設計文書の段階にある | NPC専用に閉じない発話源を用意し、像の入力を段階Cで接続する |

根拠：末尾の [R1]〜[R10]。

名前付き援助は、種類付き食料、個体別の在庫、既存の社会関係状態が使える構成を前提にする。有効化時に必要な状態を検査し、不足していれば設定条件を明示する。言語設定をONにしただけで、他の実験設定を暗黙に変更しない。

現在の生どんぐり RAW_ACORN は、この簡略ゲームでは可食として設定されている。したがって、名前付き援助の教材に使える。この設定はゲーム内の資源仕様であり、現実の食用適性の説明ではない。[R7]

現行 warn は相手の reach に対する制止であり、捕食者を見たときの一般的な危険警告ではない。wait は本人が待つ行動で、「待って」という相手への要求とは区別する。[R1]

## 3 初期語彙と文型

### 3.1 最小の表現設定

最初の表現設定を ja_simple_v1 とする。以下の表現と文型を、初期知識として与える。

| 初期表現 | 受信者側で作る解釈候補 | 作用と範囲 |
|---|---|---|
| ちょうだい | REQUEST、対象は現在の共有場面または未指定 | 既存の食料援助に接続する |
| 〈名前〉、ちょうだい | REQUEST、名前から想起した対象候補 | 初版は既知の食料分類に対応する名称を扱う |
| どうぞ | GIVE_MARKER | 譲渡に伴う表現。発話だけで取得を確定しない |
| いや | REFUSE | 対応する未決要求があるとき、その拒否として解釈する |
| これ、なに？ | NAME_QUERY | 今示されている対象の呼称を尋ねる |
| これは〈名前〉です | NAME_TEACH | 受信者が捉えた対象と、新しい呼称を結び付ける候補を作る |

「やめて」は現行の手出しへの制止と対応できるが、初回の実装単位からは外し、既存 warn の対象範囲を保った小さな追加とする。「あぶない」「ついてきて」「待って」等に、新しい認識能力や行動を暗黙に持たせない。

初期の対象名は、最小実験では「どんぐり」「くだもの」の2種類で足りる。教材を増やす場合は、既存の食材知識に対応する名前から加える。「どんぐり」は当初 RAW_ACORN の呼称として教え、加工済みの食材を同じ呼称へ自動統合しない。

### 3.2 文型を与える範囲

「これは〈名前〉です」と「〈名前〉、ちょうだい」の型は、設計者が与える初期規則である。名称の中身を学習してこの型へ挿入できても、文法そのものを自律獲得したとは扱わない。

初版は、任意の文章を解析する機構を置かない。ja_simple_v1 が扱う句読点・空白・文型を明示し、その範囲で解析する。未知の文型は未知として返す。

表面形と内部の解釈候補を分ける。別の表現設定で同じ有限のやり取りを表すことは可能だが、設定を追加しただけで任意の自然言語を理解できるわけではない。

### 3.3 語形の取り扱い

- 表記はUnicode文字列として保持する。ひらがなは初期教材の表記方針であり、内部型をひらがな専用にしない。
- 正規化はNFCと、表現設定で明示した空白・句読点の処理に限定する。
- 同じ内容の文字列は内部で共有してもよい。その識別子に意味や世界の対象IDを埋め込まない。
- 表記の照合と、対象の認識を区別する。文字列の一致を、対象認識の正しさの保証にしない。
- 初版では未知語の音の近さから勝手に別語へ置換しない。音韻的な類似や誤聴は、後から独立して追加する。

新しい名前は、空でなく、初版の教示文型と要求文型の両方へ挿入して入力上限内に収まる場合に受理する。名前の最大長は、表現設定内の文型の固定部分の長さから導出する。教示では覚えられたのに要求へ使うと切り詰められる、という状態を作らない。

## 4 発話から行動までの構造

~~~mermaid
flowchart TD
  A["話し手の観測と目的"] --> B["表現を選ぶ"]
  B --> C["発話イベント"]
  C --> D["距離と受信条件"]
  D --> E["聞き手の発話観測"]
  F["聞き手の語彙と履歴"] --> G["解釈候補"]
  E --> G
  G --> H["本人の応答選択"]
  H --> I["世界での行為と結果"]
  I --> J["各個体の経験更新"]
  J --> F
~~~

共通の流れは、観測、関係の想起、予測、行動、結果との照合、更新とする。[R11]

発話を聞いたこと、要求として解釈したこと、援助を選んだこと、実際に食料を取得したことは別の出来事として記録する。言語の追加で、資源収支や所有権を主観的な解釈へ委ねない。

送信者の内部の意図と、受信者の解釈は別に保持する。初期に同じ文型を共有していても、参照する対象、必要性、応じる価値は一致する必要がない。

## 5 データの境界

以下は役割を示す概念スキーマであり、新しい実装済みの型名ではない。実装名は既存の命名規約に合わせる。

### 5.1 送信者の発話計画

UtterancePlan は送信者側に置く。

| 項目 | 役割 |
|---|---|
| owner | 計画した個体 |
| purpose_ref | 何のための発話かを本人側で参照する |
| intended_interpretation | 送信者が意図した要求・教示等 |
| intended_referent | 送信者が対象だと考えた本人側の参照 |
| expression | 実際に発する文字列 |
| forecast | 選択時に保持した期待・費用・結果の見積もり |

意図と対象の正解候補は診断に残せるが、受信者の入力へ自動的に混ぜない。

### 5.2 世界側の発話記録と本人側の観測

世界側は配送・重複排除のため、発話ID、発話源、位置、発生時刻、宛先、受信可能期限を管理する。個体へは、そのうち観測契約で取得できた情報だけを渡す。

UtteranceObservation の中心は次とする。

- 発話の参照ID。
- 観測できた発話者の参照。
- 実際に受信した文字列。
- 受信時刻。
- その場で本人が捉えた状況・対象候補。
- 会話上の返信関係。初版で明示的に与える場合は、有限の会話管理用アダプターとして記載する。

世界が知る全在庫、正確な未観測対象、送信者の空腹・欲求・意図は渡さない。名前の問い合わせで必要な対象提示は、次節の観測経路を使う。

現行の人物IDによる識別を初版で継続する場合も、人物の外見や声から識別を学習した結果とはしない。[R4]

### 5.3 受信者の解釈

InterpretationCandidate は、受信者が観測と自分の語彙から作る。

主な状態は次とする。

| 状態 | 意味 |
|---|---|
| interpreted | 文型と、必要な対象候補を本人側で構成できた |
| unknown_form | 文型や語形を知らない |
| unknown_name | 文型は分かるが、名前との対応を持たない |
| unobserved_referent | 名称質問・教示が指す対象を観測できない |
| unresolved_referent | 候補が複数あるなど、対象を決められない |
| unsupported_scope | 文型は分かるが、初版の行動対象の範囲外 |

これらは拒否や物理的失敗と同一視しない。初版は未解決の候補を保留できればよく、毎回一つの正解を作る必要はない。

REQUESTなどの内部ラベルは、受信者側で得られた解釈の種類である。元の発話へ、送信者の正解ラベルとして後付けしない。

### 5.4 個体別の語彙関係

LexicalRelation は最低限、次を持つ。

- 所有する個体、表記、本人側の対象・関係参照。
- 出典の種類：initial_seed / tutorial_observed / npc_utterance / player_utterance。
- 誰から、いつ、どの発話で得た候補か。
- 観測できた場面の参照と、その有効範囲。
- 教示を受けた件数、使った件数、観測できた結果。互いを同じ成功件数へまとめない。
- 別名、同じ表記から出る複数候補。
- 直近の有限な出典参照と、保持・削除の記録。

同じ初期語彙を配っても、可変の語彙状態を全個体で共有しない。共用してよいのは不変の表記定義や初期テンプレートである。

世界側の食材分類に対応する既知の関係を、本人が初期知識として持っている場合は、その参照へ名前を結び付けてよい。名前を一つ覚えたときに、未知だった分類、可食性、加工法、好み、所有者を一括で新規取得したことにはしない。

## 6 名前を聞くための対象提示

「これ」は文字列だけでは対象を確定できない。最初の教育場面では、教材を一つ提示し、相手もその教材を捉えられる条件を設定する。

名称質問の開始時には、対象提示の参照と返答期限を保持する。対応する教示の受信、対象の観測喪失、会話からの離脱、中断、期限切れで質問を閉じる。閉じた質問への遅い発話は新しい観測として扱えるが、過去の成功・未達・Hを遡って書き換えない。改めて教示として使う場合は、その時点の対象観測を確認する。

### 初版の提案

1. 教材を提示する世界側の操作を用意する。
2. 個体には、通常の視認または明示した教育用観測アダプターを通して、提示対象の観測を渡す。
3. 名称質問・教示は、その時点の提示観測へ結び付ける。
4. 見えていない、提示期限が切れた、複数の候補が残る場合は、その状態を保持する。

初期教育で、既知の食料分類を明示的に示す簡略アダプターを使うことは許容する。これは初期条件として記録し、自由な視覚認識が完成したという扱いにはしない。

通常生活へ広げる段階では、誰が何を見ているか、提示を観測したかを別々に確認する。全個体が同じ対象IDを知っているから共有注意が成立した、と判定しない。

「これはなもです」と教わったときに生まれるのは、「この場面で、この相手が、私が捉えた対象をなもと呼んだ」という対応である。別名が追加されたことだけを理由に、以前の名前や情報源を誤りと判定しない。

## 7 名前付き要求から現物の譲渡へ

この接続を、初版の中心となる実装課題にする。

### 7.1 要求の送受信

送信側が既存の援助要求を選んだとき、その本人が使える名前と初期文型から表現を組み立てる。名前を使えない場合は、教示済みの一般要求「ちょうだい」を候補にできる。

受信者は自分の語彙で名前を解釈する。その対象候補に合う、自分の手持ちや利用可能な備蓄を調べ、従来の本人の必要・保持費用・相手との関係を使って応答を選ぶ。[R2]

言語が通じることは、援助を必ず行うことを意味しない。発話は、既存の行動選択へ条件を渡す。

### 7.2 指定した種類がない場合

名前を理解できたが、その対象を渡せない場合は、応じない選択や拒否を扱う。別の食材を無条件に代わりとして渡さない。代替提案の会話は後続の拡張にする。

名前を理解できなかった場合は unknown_name とし、「相手にその食材がない」「相手が拒否した」と推論しない。

### 7.3 現物選択の追加

現行の援助は食材の先頭要素に依存するため、次を追加する。[R2] [R3]

1. 受信者が解釈した対象条件から、自分の在庫内の候補を選ぶ。
2. tickをまたぐ計画には種類等の対象条件を保持する。在庫索引を、永続的な現物参照として扱わない。
3. 譲渡直前に現在の在庫から索引を解決し、対象・接触・種類・品質・期限・対応するcargo要素を、総在庫数を変える前に検証する。
4. 同じ現物を、総在庫数、cargo、種類別在庫、品質、期限へ一貫して反映する。
5. receiptと受取経験には、意図した種類でなく、実際に移した種類を記録する。

food_give!(..., i) は指定索引を受け取れるため、品質と期限を保持する既存処理を利用する。[R6]

検証から一連の移動までを一つの実行として扱う。現行communicate!は総在庫数を先に変更するため、新しい索引の検証をその呼出し後へ置かない。失敗して総数だけが変わる状態や、二回の処理で異なる現物を参照する状態を作らない。

倉庫から取り出してから渡す短い計画も、指定した種類を保持する。途中で現物が失われたり状態が変わった場合は、その実行計画を閉じるか再検討する。別の先頭食材へ黙って置き換えない。

### 7.4 元のrequestタグへの依存を外す範囲

現行communicate!は返信元のkindがrequestであることを確認する。[R1]

新しい言語経路では、**受信者が実際に観測した元発話への参照と、その受信者の解釈**から応答計画を作る。世界側では、元発話の観測・宛先・返信関係、接触、所有、在庫、重複適用を検査する。

受信者の解釈を使って原発話の記録を書き換えたり、裏側へ旧request通知を同時に配って理解を成立させたりしない。既存の物理的譲渡処理は共用できるようにし、言語経路と旧経路で二重に資源を移さない。

拒否の認識も、受信者が表現を解釈し、自分の未決要求へ対応付けた結果から得る。送信者側の拒否行為receiptや旧refuse通知を、そのまま受信者へ明示的拒否の経験として渡さない。「いや」を知らない個体が、内部タグだけでその意味を理解する経路を残さない。実際の譲渡に基づくgivenの取得証拠は、この言語上の拒否認識と区別する。現行ingestがrefuse通知を拒否経験へ使う箇所も、接続時の変更対象になる。[R17]

### 7.5 「どうぞ」と取得の区別

通常の表現生成では、「どうぞ」を実際の譲渡に伴わせる。物理的な受領は従来の譲渡結果から観測する。

単独で「どうぞ」が届いた場合、それだけで在庫増加、援助成功、目的達成、H解消を発生させない。反対に、言葉を聞き取れなくても実際に受け取った物は本人の取得経験になる。取得できたことだけで語の意味理解を確定しない。

## 8 初期チュートリアルと開始状態

初期教育の内容と順番を設定し、一通り覚えた状態から始めることを許容する。その作り方は三つを区別する。

| 方式 | 使い方 | 履歴の扱い |
|---|---|---|
| initial_seed | 覚えた語彙・文型・初期の関係を直接与える | 与えた初期条件として保持。実行していない発話や成功回数を生成しない |
| run_tutorial | 台本に沿って提示・発話・受信・使用を実行する | 教育条件は固定設定、観測された出来事は実行履歴として保持 |
| restore_tutorial_state | 実行した教育後の保存状態を再利用する | 元の履歴を継承し、読み込むたびに同じ経験を加算しない |

最初の開発段階Aはinitial_seedで進められる。段階Bでrun_tutorialを通し、同じ語彙状態の入口を使えるようにする。

### 教材の例

1. 神の像に対応する教材用発話源が、どんぐりを提示する。
2. 「これはどんぐりです」と教示する。
3. くだものについても同様に教示する。
4. Aが「どんぐり、ちょうだい」を使い、Bとの受け渡しを経験する。
5. 拒否の教材では「いや」を使い、未応答との違いを示す。
6. 未知の呼び名について「これ、なに？」を使う機会を設定する。

教育用に対象提示、発話順、応答を固定した場合は、その固定を記録する。初期語彙の習得保証を直接seedで補うなら、その補完もinitial_seedとして区別する。教育の台本を通常生活の行動規則へ残さない。

固定の教育手順はconfigured_pathsのconfigured_関数に隔離する。初期の語彙データ、世界の教材配置、教育中の行動の固定を、それぞれの役割として記載する。[R12]

## 9 経験更新とRDL上の位置づけ

### 9.1 初版の学習対象

初版で変化するものは、主に次である。

- 対象と新しい呼称の関係。
- 既知の対象に対する別名。
- 誰から聞き、どの場面で使ったかという出典と用法の経験。
- 言語を通して起きた援助・拒否・取得の結果に基づく、既存の相手予測。

文型と最初の語義は初期条件である。初版では、既知の語が自由に別の語義へ変わることや、音列が自発生成されることを必須にしない。後の拡張を妨げないよう、個体別の関係と出典を残す。

名称の教示は、一度受信すれば暫定的な対応候補として使用できる初期規則にしてよい。ただし「聞いたことがある」と「生活の中で有効だった」を別の証拠として保持する。

### 9.2 対応候補の想起

表記から有限な候補を取得し、本人が観測した場面や相手との履歴で絞る。対象特徴の比較には、既存の関係照合を適用できる範囲で利用する。

同じ表記に複数の候補がある場合は、保留や未解決を許す。名称の文字列を食料IDの大小や数値距離へ変換して、意味の近さの代わりにしない。

異なる相手からの教示や別名は保持できるようにするが、初版で情報源全体に共通の「真理スコア」を新設しない。評価は対象・問い・場面・観測結果の範囲で行う。

### 9.3 Hと目的達成

言語イベントを既存の食料獲得の成功へ直接変換しない。

- 発話が届いたことは、配送の結果。
- 語との対応を得たことは、名称学習の結果。
- 要求を理解したことは、受信者の解釈。
- 食料を取得したことは、世界での受け渡しと本人の観測。
- 本人の目的が満たされたかは、選択時の見積もりと実際の結果で評価する。

未知語を聞いた回数を、そのままHへ加えない。比較可能な予測と結果がある場合に、同じ評価対象の範囲で既存の結果評価へ接続する。未観測や比較不能は差の値に置き換えない。

例えば、要求したどんぐりと違う物を受け取った場合は、その違いを記録する。取得した物に本人にとっての価値があれば、その価値の経験は残る。「要求対象を得た」「食料が増えた」「意味が通じた」「相手が拒否した」を混同しない。意味のずれの原因を、結果だけから一意に確定しない。

T0の比較条件、T1の情報源の評価、TDの「意味を各個体の解釈と後続作用として読む」方針に合わせる。本案はGameAI内の局所実装であり、Coreの新しい原始概念やcanonical形成規則を追加しない。[T0][T1][TD]

## 10 神の像との接続

神の像は、拠点にある発話源として扱う。NPCの身体や在庫を持つように偽装して、現行のNPC専用ID検査を通さない。[R8] [R9] [R10]

発話源を、少なくともnpc、tutorial_script、player_statueとして区別する。三者の発話は、受信後には同じ観測・解釈・語彙更新へ入る。

プレイヤーの最初の入力は、短い文字列と、観測可能な範囲で示した対象に限る。像が「これはなもです」と言えば、聞いた個体に教示の経験が生まれる。全NPCの辞書や世界の食材分類を直接書き換えない。

NPCは、名前を知らず、その名前を知ることが現在の行為に関係するときに、名称質問を候補にできる。質問に必ず答える、必ず覚える、必ず信用するという通常生活の固定規則は置かない。初期教育での保証は、教育設定として別に扱う。

段階Cでは入力APIまたは簡単な実験用入力から一往復できればよい。プレイヤー向けの完成した画面、自由な文章生成、神像の自由移動は初版の必須範囲に含めない。

既存設計の、system-generatedな生活cueとプレイヤー自身の発言の区別を維持する。実験者用の全世界診断を、そのままゲーム内プレイヤーの情報へ流用しない。[R9]

## 11 時間と処理費用

### 11.1 最小の通信条件

段階Aでは、既存の近接・遮蔽・聴覚可否の条件を利用する。初期の近距離通信を、自然な音響伝搬を実装したものとは扱わない。[R1] [R10]

発話は既存の社会行為の実行機会に載せる。初版は文字数比例の発声時間や、新しい身体消費係数を追加せず、既存の社会行為の時間刻みと身体更新を基準にする。発話だけを何度も同じ時刻で連鎖実行しない。

現行の受信通知には3秒の寿命、援助の応答計画には別の5秒の期限がある。発話の発行時刻、観測時刻、応答期限の起算を記録し、期限の役割を混ぜない。語を長く発声するモデルを追加する際は、この時刻契約を改めて調整する。[R1] [R4] [R13]

新しい言語経路では、受信済み発話の参照・発話源・宛先・受信時刻を、応答計画の検証に必要な期限まで有限に保持する。返信のguardはこの受信証拠を参照し、3秒で消える現在の観測一覧だけを探さない。現在聞こえなくなったことと、以前に受信した証拠が失われたことを分ける。応答できる期限は、対応する計画側の期限で判定する。

帰還後の計算停止は、現行の社会通知と同じ責務の入口で解除できるようにする。一方、睡眠中・倒れた状態の感覚遮断を、言語機能の追加だけで無条件に解除しない。届かなかった発話を起床後に自動学習しない。

### 11.2 更新する機会

主な処理は、既存の判断機会、発声、受信、応答、結果確認、名前の教示に限定する。全tickで全語彙、全相手、全過去会話を走査しない。

既知の表記は索引から候補を取り出す。語彙追加・変更時に索引を更新する。相手ごとの経験は必要な範囲で想起し、直近の処理済み発話を毎tick解析し直さない。

### 11.3 初版の暫定予算

下表は本案の初期値であり、生物学的な定数や性能実測から得た値ではない。実装前に既存の同役割の設定を確認し、同じ役割なら再利用する。数値が同じだけの別概念は統合しない。[R13]

| 設定案 | 初期値・単位 | 役割 |
|---|---|---|
| scene.simple_language | false | 明示的に有効化した実験で導入 |
| language_profile | ja_simple_v1 | 教示済みの表記・有限文型 |
| language_initialization | initial_seed | 段階Aの開始方式。段階Bで実行教育を追加 |
| max_utterance_chars | 64 Unicodeスカラー値／発話 | 入力と保存の上限。UTF-8バイト数や発音時間ではない |
| lexical_relation_limit | 128関係／個体 | 名前・対象・条件の対応の容量 |
| inbox_turn_limit | 16件／個体 | 未処理受信の容量 |
| pending_initiated_dialogue_limit | 1件／個体 | 本人が開始して結果待ちとなる要求・名称質問の範囲 |
| dialogue_history_limit | 64件／個体 | 直近の詳細履歴。累計を別に保持 |
| lexical_source_ref_limit | 16件／関係 | 出典の詳細保持量 |
| interpretation_candidate_limit | 最大8件 | 既存の想起予算に合わせる提案。語彙全体を評価しない |
| reception_lifetime | 現行3秒を基準 | 発話観測の有効期間 |
| aid_reply_window | 現行5秒を再利用 | 援助の未決計画の期限 |
| name_reply_window | 5秒 | 即時応答する初期教材用の暫定値。援助期限とは別の設定 |

本人が結果待ちであっても、他者の発話の観測と応答を一律に禁止しない。自分の未決要求と他者への応答は、別の発話ID・返信参照で保持する。返答を出したことで、元の未決要求のreceiptを失わないようにする。

名称質問の5秒は、人間の実時間での入力速度を保証する値ではない。段階Cの遅いプレイヤー発話は、新たな対象提示と教示として受信できる形を用意する。実時間UIの進行速度や一時停止は、別の設計課題として扱う。

上限到達時は、採用保留・削除・受信期限切れ等を記録する。容量から落ちた候補を「知らない相手」「拒否」「成功」へ読み替えない。入力が長すぎる場合は、名前の途中を切って別語として学習せず、入力条件外として返す。

身体・認知・世界・暫定固定判断の値を分け、LW_Parameter_Catalogへ用途と単位を追記する。

## 12 保存と再開

保存対象に、個体別語彙、初期設定の版と由来、出典、未決会話、受信処理済みID、結果との対応、必要な乱数状態、有限キューを含める。

同じ発話IDの再送は、同内容なら既存結果を返し、内容が異なれば不整合として拒否する。同じ文字列を本人がもう一度発する場合は、新しい発話IDを与える。再送と再発話を区別する。

意味理解の失敗と、記録IDの破損は別である。誤解を許容するために、出典や返信関係の整合性を曖昧にしない。

### チュートリアル後の状態

現行の保存APIは日末チェックポイントであり、任意の教育終了時点をそのまま保存・再開できるAPIではない。[R8]

初版の選択肢は、次のように扱う。

- 開始時の語彙だけを与える場合は、明示的なinitial_seedを使う。
- 実際の教育履歴を再利用する場合は、まず既存の日末保存の境界で再利用する。
- 任意の教育終了直後を保存したい場合は、開始位置と実行状態を含む別の保存契約を追加する。日末の途中状態を日末として保存しない。

既存の日末checkpointを再開するときは、元の教育設定を含む同一の入力identityを維持してresumeする。restore_tutorial_stateは再開手順を表す呼称であり、run_tutorialだった保存元の設定を別の値へ変えて検査を回避するモードにはしない。教育後の状態を異なる条件の新規実験へ移植する機能は、独立した初期化契約として扱う。

新しい言語状態を加えたチェックポイントは、新しい同一ソースの下で検証する。古いチェックポイントを読むためにソースハッシュ、Julia版、入力identityの検査を外さない。

## 13 導入段階

### A 教示済み語彙から既存の援助へ

**範囲**

- initial_seedによる個体別の語彙・文型。
- 近距離の短い発話。
- 名前付き要求、譲渡に伴う「どうぞ」、拒否。
- 受信者が解釈した種類から現物を選ぶ接続。
- 結果の記録、保存、重複排除。

**終了条件**

Bの在庫を「先頭にくだもの、2番目にどんぐり」とし、Aの「どんぐり、ちょうだい」を受信者の語彙で解釈できる。援助を選んだ場合は2番目のどんぐりを、品質・期限を保って渡せる。応じない選択も残る。未知語や対象不明を、旧requestタグの裏経路で解決しない。

### B 教示と名称の追加

**範囲**

- 「これ、なに？」「これは〈名前〉です」。
- 一つの対象を提示する最小の観測契約。
- run_tutorialと、教示による名前・別名の追加。
- 名前を聞いた個体から別個体へ教示できる同じ経路。

**終了条件**

未知だった呼称「なも」をどんぐりへ結び付け、その個体が後で「なも、ちょうだい」と使える。受け手が「なも」を知らなければ未知として残る。その受け手も教示を受けた後は対応を利用できる。全員の語彙が一括更新されない。

### C 神の像からの入力

**範囲**

- 像という外部発話源。
- 教材スクリプトとプレイヤー入力の由来の区別。
- 同じ発話・受信・解釈経路を使った名称質問と返答。
- 実験用の短い入力API。

**終了条件**

NPCの質問に対し、プレイヤー入力の名前を像が発し、聞いた個体だけにその対応の候補が残る。世界の分類、全個体の辞書、NPCの行動を直接書き換えない。

Aを最初の独立した変更として実装する。BとCはその確認後に接続し、各段階で、実装した範囲と残る範囲を明記する。

## 14 検証と観察

初期設定・教育台本・検証用の固定選択を明記した小さなケースで接続を確かめる。通常生活では、会話回数や必ず譲渡することを合格条件にしない。[R12]

| 検証 | 確認する結果 |
|---|---|
| 初期語彙からの解釈 | 教示済みの句と名前から、本人側の要求候補が得られる |
| 名前付き現物選択 | どんぐりが先頭以外にあるときも、解釈した対象と実際の移動が対応する |
| 語彙差 | 一方だけが知る名前は、他方へ自動共有されない |
| 対象提示の不成立 | 未観測・複数候補・期限切れを、正解IDで埋めない |
| 意図の裏経路 | 同じ受信列・観測・本人状態・乱数状態で、送信者の診断用意図だけを変えても解釈が変わらない |
| 未知表現 | 旧requestタグから要求が成立したことにならない |
| 未知の拒否表現 | 「いや」を知らない受信者が、送信者の内部REFUSEや旧通知だけで明示的拒否を学習しない |
| 「どうぞ」だけの受信 | 在庫・取得成功・H解消が発話だけでは発生しない |
| 理解と応答 | 要求を理解しても、本人の通常選択で拒否できる |
| 未応答と拒否 | 聞き逃し、未知語、対象不明、期限切れを明示的拒否へ統合しない |
| 譲渡の収支 | 総数・種類・cargo・品質・期限・receiptが同じ現物を指す |
| 在庫の並び替わり | 計画後に在庫の位置が変わっても実行直前に解決し、総数を変える前に現物の対応を検証する |
| 受信寿命と返信期限 | 現在の観測一覧から発話が消えても、有効な受信証拠と未決計画に基づき返信を検証できる |
| 再送と再発話 | 同IDの再送は二重処理せず、新IDの同じ語句は別の発話として扱う |
| 別名と曖昧さ | 新しい別名で既存名が消えず、同じ表記の複数候補を保持できる |
| 初期教育の由来 | seedと実行教育が分かれ、未実行の会話を成功件数へ数えない |
| 名称質問の終了 | 対象喪失や期限切れで閉じ、後の要求・質問を塞がず、遅い返信で過去の評価を書き換えない |
| 名前の長さ | 教示で受理した名前が、要求文型でも上限内に収まり、途中切断されない |
| 保存再開 | 未決会話を含め、同一条件の継続実行と再開実行で結果・学習・乱数の進行が一致する |
| 容量 | 上限で落ちたものを記録し、物理的成功や相手の拒否へ変換しない |
| 神の像 | 外部入力が通常の受信・解釈を通り、語彙や世界を直接書き換えない |

### OFFとONの比較

OFFでは新しい乱数消費や発話処理を入れず、既存の行動と世界結果を維持する。

ONでは行動・学習が変わるため、全ログの一致を求めない。資源収支、ID、所有権、保存再開などの契約を確認し、そのうえで語の使用と関係の変化を観察する。

### 性能の記録

同じ新ソースと揃えた初期条件で、実行時間、割当量、GC、発話数、受信件数、解析回数、解釈候補数、経験検索数、キュー最大長、語彙件数を記録する。

生活全体のON/OFFでは行動数も変わる。総時間差を言語処理だけの費用と断定しない。純粋な処理費用を調べる必要が出た場合に、固定した短い発話・観測列で別に測る。性能の改善率や許容率を、実測前に保証しない。[R14]

## 16 Codexへの引継ぎ指示

この設計案を、Julia LWに対する段階的な実装課題として扱う。

1. 実装開始時のHEAD、AGENTS.md、共通実装方針、設定経路、数値設定一覧を確認する。本案の調査基準からの変更点を先に把握する。
2. 最初は段階Aを実装する。既存のrequest表示の置換だけで終えず、受信者の語彙解釈から指定食材の現物選択まで接続する。
3. 初期の語句・文型・対象名を与えることは、今回の設計方針で許容されている。設定内容を説明し、固定教育・初期seedの由来を記録する。
4. ON/OFFを分け、OFFの既存経路と、新しい言語経路の物理契約を維持する。原発話と解釈を別に保持し、意味タグの裏経路を作らない。
5. 同じ物の二重移動、先頭食材の取り違え、未応答の拒否化、checkpointの状態漏れを重点的に検査する。
6. 小さな制御ケースで接続を確かめた後、短い生活実験で、利用状況と処理費用を確認する。
7. 完了報告には、実装したこと、与えた初期条件、経験から更新したこと、計測結果、残る範囲を分けて記載する。
8. 段階B・Cへ進む際も、同じ受信・解釈・更新の入口を使う。一般会話や音声波形へ範囲を広げない。

設計で未固定の関数名やファイル分割は、現行コードに合わせて決めてよい。世界の収支、本人の観測範囲、初期設定の由来、語彙と物理行為の境界は維持する。
