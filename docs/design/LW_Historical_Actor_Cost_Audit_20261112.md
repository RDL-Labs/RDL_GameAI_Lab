# 歴代IDの蓄積と生態系の実行費用

2026-11-12。対象HEAD `fcf7048`。人間だけの候補見積もり比較とは独立した課題。
ユーザー追記に従い、今回は静的確認と次の小実験の整理まで。速度計測・最適化の実装は現行比較終了後。
履歴を消す、IDを詰め直す、認知や繁殖の規則を変える案ではない。

## 現時点で確認できた構造

Nを歴代配列長、生存数をA、自力採食/移動の対象数をM、授乳対象となり得る幼体数をYとする。
aliveとlife.movingはBitVectorだが、各ループは主に1:Nを走査してビットで除外する。
Mは単なる成体数ではない。離乳前の自力採食も既存のconfigured_rabbit_self_feedingに依存する。

|箇所|走査・初期化|頻度と注意|
|---|---|---|
|LWGrazing.prepare!|overrides全消去、全aliveの走査|毎tick。自力採食できない個体は後段で除外|
|configured_rabbit_nursing!|全aliveを走査しmovingを書換え、母子別一覧を構築|繁殖ON時毎tick。pending/targets更新もあり|
|configured_rabbit_nest_preparation!|全aliveを走査して出産前の雌を選ぶ|有効時毎tick。場所候補の構築自体は毎tickではない|
|LWGrazing.advance!|警戒/逃走回数更新、最後の餓死判定で各1回全走査|毎tick、計2回|
|Herbivores.step!|身体/採食要求と移動/消費更新で各1回1:N|毎tick、計2回。N=length(a.x)、moving/aliveで除外|
|prepare_rabbit_neighbor_batch!|1:N走査、slots全面fill!|バックエンド有効時。候補が不要な個体も最初に除外判定|
|rabbit_advance!|全aliveから従属幼体を選ぶ|毎tick|
|rabbit_nurse!|全aliveから母・不足・距離条件の合う幼体を選ぶ|毎tick|

上記だけで、繁殖・巣準備・近傍バッチが有効なtickには構造上10回の歴代走査。
バックエンドなしなら近傍の1回は早期return。これは静的な回数で、実測の呼出しカウンタでも全システムの総数でもない。
捕食者/猛禽/匂い側の獲物走査は別に残る。各ループ本体の費用は生存/状態/地形で大きく変わる。

日次にはrabbit_daily!の妊娠処理、reserve_sample、雄の空間表、雌の受胎判定が全走査する。
**妊娠処理は死亡個体も対象**。死後の投資清算を行ってからdue/litterを消すため、生存一覧で代用してはいけない。
snapshotの履歴全件出力・収支検査は日末系であり、毎tick走査と分ける。

## 作業領域・出生

近傍バッチのqueries/gpu_queries/gaps/clear_results/slots/originsは、候補実数やAではなくNで確保する。
容量がNより小さいと全6配列を作り直すため、出生でNが増えると次回prepareで再確保する。
64bit環境の配列データ部分は約512N bytes。slotsの全面初期化は約72N bytes/tick。
候補の幾何評価自体はused件だけであり、GPU転送・判定が常に歴代数分あるわけではない。

Herbivores.step!のdemand/long_demand全面初期化は**地形セル数**に比例する。
歴代IDによる負荷とは区別する。requestsは歴代数分を保持するが、毎tick全消去はせず対象個体の値を書き直す。

rabbit_birth!は多くのVectorへpush!する。この内部容量拡張はJuliaの容量管理次第で、毎出生の全コピーとは断定しない。
一方、`a.counts=vcat(a.counts,zeros(...))` は各出産で行列全体を再作成する。
通常6列なら既存部分は約48N bytes。この頻度は毎tickではなく出産イベント数に依存する。
現行のallocation_limit=10000は歴代配列長に対する実験停止上限。今回この上限は変更しない。

参考として既存3000日試験のprogress.jsonには、生存142・累積出生2810が記録されている。
初期個体も別に存在するので、歴代数と生存数の隔たりがあることは分かる。
正確なN/M/Yは保存状態を読む次回に集計する。現時点の時間寄与率は未計測。

## 次に試す順序（費用が確認できた箇所だけ）

1. 生存数が近い少数の保存状態でN/A/M/Yと近傍のused/容量を集計。
   走査・fill!・容量拡張・出生時countsコピーを短い局所計測で分ける。
   総時間の差をそのまま歴代数の効果としない。網羅的な大規模試験からは始めない。
2. 近傍作業領域の容量に余裕を持たせる、または前回使った列だけを消す小変更を優先候補にする。
   古いslotを現tickの結果と誤認しないことを検査。出生のない安定tickと出生直後を両方見る。
3. 歴代走査の寄与が大きければ、実行用のalive/moving/dependent一覧を検討する。
   最初は段階ごとに1回作る一覧の共有でもよい。イベントごとの完全な増分索引をいきなり全域へ入れない。
4. countsの容量管理は実測で目立つ場合。現在の行列サイズをID数とみなす出力・検査もあるので別変更にする。

## 索引化する場合の最小条件

- 永続IDは配列添字のまま。昇順の対象一覧で現行順を保つ。削除時に末尾と入れ替える方式は避ける。
- prepare→moving更新→身体/採食/移動→授乳/日次出産→餓死→捕食の段階順を保つ。
- 死亡経路は通常の餓死、妊娠費用での死亡、通常捕獲、確率捕獲、猛禽捕獲を確認する。
  単独動物実験でaliveを直接変更する経路もあるため、一箇所の関数だけをフックして完全対応としない。
- 母の死亡による自力採食判定、成長・離乳、出生直後のmoving=falseも一覧更新へ反映する。
- 死亡した妊娠個体の清算は別のpending対象などで維持する。履歴参照を削除しない。
- 派生索引は復元後に再構成できるものにする。バックエンドの作業領域は既に外部Refで、身体モデルへ埋め込まない。
- 同じ短い再生区間で身体/行動/草・エネルギー収支/母子参照/内部状態/RNGを比較する。
  出生・死亡・離乳を含む小ケースを足し、保存・復元後の再構成を確認する。
