## 1. 今回の決定

初期の同等移植は、移植ミスと設計変更を分けるために有効だった。しかし、旧実装を変えないこと自体が新実装の計算・メモリ費用を増やすなら、その一致要求を維持することは目的ではない。

**旧実装は比較対象の一つであり、正解そのものではない。** 新しい実装では、行動時刻・選択列・Hの中間値・履歴形式が変わっても、それだけで不合格にしない。変化の内容と、残った関係応答、計算費用を評価する。

ユーザーの「同一性はあくまで、らしさ」という解釈を、本書では次の開発基準として扱う。

> 同じビット列や同じ動作列であることではなく、選んだ観測・評価の境界において、経験・現在条件・関係拘束に応じた傾向の持続と変化が認められること。

これはユーザー意向に基づく**GameAIの評価方針**であり、T0にそのまま記載された定義を引用したものではない。プログラム上のオブジェクト同一性や、個体・操作IDの区別とも別の話である。[U1–U2]

## 2. 旧方針のどこを変更するか

| 項目 | これまでの強い条件 | 新しい方針 |
| --- | --- | --- |
| 行動の一致 | 同じ時刻・同じ候補・同じ動作列 | 関係条件に応じた応答を見る。時刻・回数・経路の差は許容できる |
| 状態の一致 | H等の全中間値・全出力が一致 | 必要な役割・応答傾向を評価する。中間値の変更も試せる |
| 更新の戻り値 | 毎回、独立して変更できる別状態を返す | 新経路ではその場での更新を許す。別状態を返すことを必須にしない |
| 根拠・履歴 | 全件保持、各状態から完全に辿れる | 要約・統合・間引き・忘却・保持範囲の限定を許す |
| 過去状態 | 全更新前の状態を不変のまま残す | 比較・分岐・診断に必要な範囲だけ保持する |
| snapshot | 通常更新に付随して作成 | 必要な場面で、必要な範囲だけ明示的に取得する |
| 数値精度 | 既存の許容差・型を全域で維持 | 計算費用に見合う精度を選ぶ。元の許容差は新設計へ自動継承しない |
| 完全一致テスト | 不一致があれば採用不可 | 主に差の所在を調べる診断へ位置づけ直す |

変更は**新しい再設計実験に適用する**。J0〜J3、A0〜A2、型整理・巡航診断などの過去の契約や報告は、その時点の条件と結果として残す。以前の不一致を後から一致だったことにしたり、未検証の機能を検証済みにしたりしない。

旧コピー契約を検査するテストは、旧実装の参照検査として隔離するか、新経路の契約に合わせて置き換えてよい。**そのテストを通すためだけに、不要な全状態コピーを新経路へ再導入しない。** 古い失敗を無言で隠すのではなく、どの契約を変更したため検査を変えたかを短く残す。

既存の本線や公開APIへ接続する際は、対象の呼出し側も新契約に合わせて変更する。移植実験の方針変更を、無関係な利用側の契約を黙って破る根拠にはしない。

## 3. 「だいたい合っている」を何で見るか

「らしさ」は、正解動作列を少し緩く指定することではない。**条件を変えたとき、何に応じて挙動が変わるか**を評価する。次は評価軸の案であり、すべてが現在の実装で成立済みという意味ではない。

| 評価軸 | 確認したいこと | 必須にしない一致 |
| --- | --- | --- |
| 経験が後に効く | 援助が得られた／得られなかった経験が、後の相手選択へ寄与する | 同じ相手に同じ回数頼むこと |
| 未解消に応答する | 現在の方法で不足が続けば、見直し・別方法・探索等へ圧力が生じる | Hの全数値、同じ切替秒数 |
| 現在条件に接続する | 頼れる相手でも、今は届かない・所持がない・本人に必要がないなら選択が変わる | 過去に成功した相手を必ず選ぶこと |
| 傾向が持続・変化する | 異なる経験を与えた個体の傾向が区別でき、その後の経験によって変化し得る | 性格ラベルの固定、永続的に同じ行動をすること |
| 観察する価値がある | 目的・状況・経験と行動の繋がりを追え、次の挙動が気になる | 変化の回数や「面白い出来事」を台本で保証すること |

例えば、旧版が「Bに3回断られてCへ」、新版が「2回でCへ」でも、直ちに失敗ではない。B/Cの応答経験を入れ替えれば選択傾向も変わるか、代替相手が見えなくなれば現在条件へ応答するか、といった対照を見る。

反対に、最終的にCを選んだことだけでは足りない。相手や経験を変えてもC固定なら、今回狙う関係応答の再現とは異なる。

**モデルが行動へ作用する機会がない条件では、行動差0を学習機構の失敗と即断しない。** 既存A2は、食料を確保した後に再要求しないため、社会期待の形成差が後続行動へ出なかった。必要なら、再び選択が生じる短い条件を別に用意する。正解の相手を直接指定して差を作らない。[R2]

## 4. 許容する簡略化

以下は実験してよい選択肢であり、全部を一度に実装する指示ではない。

### 4.1 現在状態はその場で更新してよい

局所H、現在の試行、候補評価などを、更新担当の処理が直接変更する構成を認める。呼出し前の全状態が後から参照可能であることを、通常更新の契約から外せる。

設計例として、更新用の `update!` と、写し取得用の `snapshot` を分ける。名前は例であり、既存APIとして存在すると主張するものではない。更新用処理は、同じ状態を更新して返しても、変更の有無だけを返してもよい。

### 4.2 履歴は影響を残すために保持する

古い経験の全件保存ではなく、相手別の成功・不成立の要約、最近の経験窓、重要な例だけの保持などを選べる。要約の再解釈や更新も認め、内部記憶全体を永久不変にする必要はない。

保持項目は、対象・結果の種類・期間・更新規則など、当該判断に必要なものへ絞る。全要約から全原記録へ戻れることは必須にしない。**捨てた情報は復元・監査できないと明記し、覚えているふりをしない。**

### 4.3 新しい材料がない更新は省略できる

受理側が追加・変更を通知し、全履歴の再走査をせず現在状態を維持する案を試してよい。新規0件で独立した写しを作る必要はない。

ただし、新規0件を判定するために全件を毎回コピー・ハッシュ・比較するのでは、費用の移動になる。変更通知や版管理を採用する場合、その管理費用も実測へ含める。

新規経験がなくても、身体・時刻・危険・相手の所在などは変わり得る。省くのは不要な履歴処理であって、必要な現在条件の確認まで無条件に止めることではない。時間による忘却等を採用した場合、その更新も別に扱う。

### 4.4 記録・精度・更新頻度も目的に合わせる

通常運転では全状態の毎step保存を求めない。短い診断区間、遷移時の小さな記録、必要時のsnapshotで判断できるなら、それを選ぶ。

数値の丸め、近似、候補数の制限、更新頻度の変更も選択肢になる。ただし、Bの変更、B内部の区別としてのρ変更、更新周期の変更、キャッシュ再利用は区別する。すべてを「ρを下げた」と呼ばない。[R3, S3]

## 5. 精密に残す範囲も、必要なものへ絞る

近似の許容は、意図しない実装事故を「らしさ」で免責することではない。初回は次の小さな境界を残す。

**Worldの実行成立。** 宣言した資源収支、実行時の接触・身体条件、操作再送の扱いは確認する。これらの規則自体も設計変更は可能だが、変更を宣言せずに食料が二重生成されることとは分ける。重複防止に全操作履歴の永久保存を義務づけるものではなく、必要な再送範囲を決めてよい。

**個体と情報の区別。** 同じデータを共有した事故で他個体の状態が書き換わること、取得していないWorld情報を知らないうちに選択へ戻すことは避ける。意図的な情報共有・知覚モデルの変更とは区別する。忘却や要約を認めても、存在しない経験を実体験として記録したことにはしない。

**名前と実装の対応。** 本実験は `gameai_local` を中心とする。局所H・選択閾値の近似を、canonicalなE/H/T1の完成と呼ばない。canonicalな比較を実行すると明示した箇所では、同じ更新前M_BによるF/F′等の条件を守る。ただし、その比較に必要な有限の構造・条件を保てばよく、全Worldや全履歴の複製、全過去版の永久保存を求めない。[S1, R3]

本書はT0の改訂ではない。Coreの定義に届く変更を試す場合は、局所的な借用・近似として示すか、別のCore改訂案として扱う。

## 6. テストの役割を変える

### 採用判断に使う検査

少数の短いケースで、経験の効果、未解消への応答、現在の実行条件、必要な収支を確認する。失敗理由を切り分けられる程度の記録でよく、常時の巨大な履歴保存は必須にしない。

### 診断へ下げる検査

旧実装との全動作列一致、Hの全中間値一致、固定された全JSON一致は、差の発見に使う。**差が出たことだけで、新設計を不合格にしない。** 変化が小さいか、許容する近似か、望ましくない機能喪失かを判定する。

### 新契約では廃止・変更できる検査

「更新の戻り値は必ず別オブジェクト」「すべての旧状態を変更可能なまま独立保存」など、コピー方式自体を要求する検査は、新経路では外せる。明示的に独立した写しを提供する `snapshot` だけに、対応する検査を残せる。

テストの期待値を結果へ合わせるだけではなく、**旧テストは何を守っていたか／今後は何を守るか**を一言記録する。旧参照版はGit履歴等から再取得できればよく、通常運転で二つの実装を常時並走させる必要はない。

### 検証費用にも上限を置く

変更中は関連する単体試験と短い応答対照を中心に回す。統合の節目で代表的なA1/A2や適切な回帰を確認する。毎修正で全系列・長期運転を要求しない。長期の忘却・資源推移など、本当に長い時間を問う場合にだけ長期試験を行う。

何を未実行としたかは報告するが、未実行があるだけで局所的な試行を禁止しない。必要な検査項目を増やす際も、守る挙動と検証費用が釣り合うかを考える。

## 7. 次の最小実験

**第一候補は、局所援助状態の「新規根拠0件／1件」の更新経路。まず毎回の全状態コピー要求を外す。** 大規模な不変データ基盤、共通DSL、全履歴再生装置を先に完成させる必要はない。

| 手順 | 作業 | 最小限の成果 |
| --- | --- | --- |
| 1 | 現在の呼出し側が旧状態の独立性を実際に必要としている場所を確認 | 変更するAPI契約と、必要なsnapshot地点の短い説明 |
| 2 | 小さな新経路でその場更新・追加材料の処理を試す | 新規0件で全履歴コピーを行わない実装。必要なら呼出し側も調整 |
| 3 | 短い関係応答・実行成立の試験と、速度・割当の測定 | 旧版との差、保たれた性質、費用を示す小さな報告 |
| 4 | 必要に応じ、代表的な移動／社会／Sleepの接続を確認 | 局所改善が接続先を壊していないかの判断材料 |

最初から忘却・新しいH則・ρ遷移をすべて導入しない。一方、完全同値が維持できないという理由だけで試行を停止したり、コピー必須へ戻したりもしない。独立性を捨てるAPI変更と、記憶の要約で応答が変わる変更は、可能な範囲で分けて記録する。

### 比較の出発点

直前の保存診断では、64件の受理済み履歴に対する単発更新は次だった。[R1, D1]

| 条件 | 更新時間中央値 | 累積割当 | 入力走査 |
| --- | ---: | ---: | ---: |
| 新規0件 | 0.360425 ms | 462,224 bytes | 64件 |
| 新規1件 | 1.053799 ms | 1,136,528 bytes | 65件 |

これは単一クラウドjobの局所値で、現在環境での速度保証ではない。累積割当は保持量やピークRSSではない。変更後は、可能なら同じ環境で変更前も測り直す。

新経路で全入力の提示から増分通知へ変えるなら、通知・検査・必要な記録更新までを含めて測る。snapshotが実際に必要なら、その取得費用も使用頻度に応じて別途示す。**古い処理の費用を受理側やログ側へ移しただけで、高速化したと扱わない。**

まずは3・16・64件等の小さな条件で、新規0件と1件を複数回計測する。必要に応じて、小さな統合区間を一つ測る。起動込み／準備後、累積割当／保持量・RSSは混ぜない。未測定の指標は未測定とする。

採用に固定の速度倍率は置かない。差がばらつきに埋もれれば未判定でよい。「少しだけ速いが、欲しい関係応答を大きく失った」ものを自動採用しない。「動作列は変わったが、役割が残り大幅に軽い」ものは採用候補にする。

## 8. Codexの報告形式

報告は次の欄で足りる。全トレースの添付を常時必須にしない。

| 欄 | 記載すること |
| --- | --- |
| 変更 | どのコピー・走査・保持・精度・更新条件を変えたか |
| 失うもの | 復元できなくなった履歴、旧API保証、細かい差等 |
| 残ったもの | 確認した関係応答、個体差、実行成立の範囲 |
| 旧版との差 | 回数・時刻・値・選択の変化。差がなければ、その有限範囲で差なし |
| 費用 | 測定条件、時間、割当等。局所値と全体値を区別 |
| 検証範囲 | 実施・失敗・未実行。比較できなかった理由も残す |
| 判定 | 採用候補／要調整／不採用／未判定と、その理由 |

コードが動いたことと、採用を判断できることは別である。観察上の「らしさ」や面白さが未確認なら、移植の数値一致だけで確認済みにしない。

## 9. リポへの反映方針

本書を設計文書として置き、次の実験契約から参照する。READMEまたは文書状態一覧には、**「完全同値は診断用。コピー・保存・近似を見直し、関係応答と費用で評価する」**と短く記載する。

過去の実験証拠を一括改名・改訂せず、新実験で変更した契約を識別できるようにする。新しい定数・イベント・権限・基盤を増やすこと自体を成果にしない。目的を達成する最も小さな変更から進める。
