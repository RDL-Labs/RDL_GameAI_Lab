# 加工後の見込みから呼びかけへ返答する局所実験

開始HEAD `49a6098`。焼き魚を要求された相手が生魚だけを持つケース。
通常の品目一致だけでは返答が作れなかったため、既存 `food_use_forecast` を再利用する。

## 接続と境界

初回局所検査では `processing_requests=true` のみ。通常接続は下記の追記を参照。
このフラグがOFFの通常呼びかけは現物同士のまま。

1. 呼び手が加工できる場合、「生魚でも自分で焼ける」という条件を発言へ追加する。
   自分のMBで想起した食品・現在使える設備・既存加工知識から計算する。
   相手の倉庫や設備へ直接アクセスしない。発言に塩の個体IDは渡さない。
2. 返答側は現物、生魚の引渡し、自分で加工してからの引渡しを比較する。
   加工費用は既存の見込み式を使って本人の交換勾配から引く。自動的な成立にはしない。
3. 生魚を渡す場合、交渉品目は生魚、最終目的は焼き魚として分離する。
   呼び手は提示前にも自分の設備・塩を再確認する。
4. 自分で焼く場合、未完成品は公開在庫にしない。通常の取り出し・加工・保管後に初めて
   焼き魚1個を広告し、既存の現物交渉へ渡す。加工だけで交換成功を記録しない。

塩焼き魚には認識済みで所有している岩塩が必要。設備なし・未知の食品・加工OFFでは
その変換を見込めない。出せる対価が空の場合も今回の処理では返答が作れず、別課題のまま。

## 暫定設定・限界

`configured_paths/camp_trade_processing.jl` に取り出し→加工→保管の手順を隔離。
加工知識は既存の初期知識、設備は現在地から届くものだけ。設備までの移動計画は今回含めない。
局所テストの要求は明示的な「焼き魚」で固定し、要求品目の自然な選択頻度を測らない。
加工が可能なら、元の欲求計算が初めから生魚を要求する場合もある。

自分で焼く返答を選んだ時、返答時の所要見込み（既存加工120tick＋取出し・保管各1tick）と
既存の交渉待ち128秒から期限を一度設定する。途中で期限を延ばし続けない。
費用は既存food_use_forecastの食事まで含む保守的な見込みで、厳密な加工単体費用ではない。
先に加工してから現物を交渉する局所手順なので、加工しても相手が見送ることはある。
将来の価格合意・加工依頼契約・一般的な子MBの計画はまだ扱わない。

## 検査

`julia --startup-file=no --threads=1 --project=. experiments/social_relationships/camp_trade_processing_checks.jl`

返答側の食品は生魚8個のみ、呼び手は果実8個、食品の味・姿の記憶あり。
両方式32シードずつ。交換成否は通常の確率選択に任せる。
自分で焼く方式は実際の120回の加工、身体の作業可否、加工練度、食品収支を通す。
受取側が焼く方式も、成立後に生魚を取り出して焼き魚になるまで物理処理を検査する。

結果：両方式とも32/32で返答。供給側が焼く条件は交換3/32、受取側が焼く条件は18/32。
Julia 1.13.1 / 1 thread、既存呼びかけ110＋加工境界16＋両方式357、計483項目PASS。
交換成立後の食品と加工数、資源収支を確認。返答・加工を交換成功とは数えていない。
これは局所の初期記憶・備蓄・身体条件での値であり、長期の成立率や方式の優劣ではない。

## 通常LWへの接続（2026-11-26、開始HEAD c499b44）

`scene.camp_trade_processing=true` で、呼びかけ・返答・提示前の再確認へ加工見込みを接続する。
既定false。`camp_trade_calls=true` が必要。受取側は生魚そのものを要求することもでき、
通常の食事判断が自分の設備・記憶から加工候補を評価する。生魚を必ず要求・加工させない。

供給側の準備は暫定固定の `configured_camp_processing_plan`。

記録は camp_trade の preparation / prepared_supply_ready、行動は camp_trade_prepare。
