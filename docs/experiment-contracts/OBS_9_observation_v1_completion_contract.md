## 1. 必要条件と、最後の十分条件

観測側が保証する必要条件:

- 個体別profileのもとで異なる有限観測を生成し、個体を混線させない。
- 近景・遠景・聴覚の取得時刻、取得姿勢参照、profile版、coverage、欠落を保持する。
- 遠景・聴覚へ真のWorld対象IDや正確なWorld座標を漏らさない。
- 遅延・拒否・再送で取得時点を変更せず、取得と配送を区別する。
- 生活中も観測配送と身体操作の権限を分離し、生活優先で有限Probeを中断できる。
- 後段で比較可能／比較不能、候補あり／なし／未確定を区別できる。
- 見えなかった記録と、取得不完了・比較条件不足・操作中断を区別できる。

最後の十分条件は、同じ継続WorldのA/B生活runで近景・遠景・聴覚・限定Probeを併走させ、
個体混線・二重取得・二重身体作用・旧応答の誤適用を起こさず、有限Food生活Acceptanceが完了すること。
既存の個別成功の寄せ集めだけではこの統合条件を満たしたことにしない。

OBS-0〜6E（取得・保存・配送）→ 7A/7B（比較条件・候補）→ 8/8B（再取得・調停）
→ **OBS-9（同一環境への統合受入）→ 観測基盤v1 COMPLETE**。
COMPLETE後は神経・解釈・Goal・Trajectoryの検証へ戻る。観測能力の追加を自動的な次工程にしない。

## 2. 範囲と既存機能の接続

新しい感覚器・推論・対象同定は作らない。OBS-6Eの共通センサーと取得記録、8Bの個体別調停を接続する。
試験側が受理済み遠景frame・特徴・問い・操作IDを明示する方式を維持する。
AのProbe中にBの生活を止めない。A/Bの役割を入れ替えたrunも確認する。

既存のfixture-life-sensory / fixture-life-sensory-compact（各revision 1）をA/Bに割当てる。
現行値は近景半径が両方12、聴覚gainが1 / 0.25。profile独立性はIDだけでなく実取得差と
一方の状態変更が他方へ及ばないことで検査する。近景12/8の既存単独回帰は別の証拠として残す。
遠景は双方とも距離(12,64]・水平90度・垂直60度・5度区分・最大4特徴を維持する。

8/8Bの許可表はfixture-distant-enabled限定であるため、life profileをそのまま渡しても成立しない。
OBS-9専用規則版`obs9-v1`で上記2profileの視覚条件を明示的に許可し、sourceとtargetは同じ個体・

近景の既存Food/Base IDは有限な可視範囲の生活契約に属する。遠景・聴覚に結合する正解キーとして
転用しない。実験者のWorld位置・正解IDはharnessの期待値にだけ使用する。

## 3. 共有する有限予算

初版は各run最大6秒、250000µsのtick、A/B各1個体。独立runでシナリオを切り替える。
近景は各tick最大1回、聴覚は250000µs窓、遠景は4tickごと最大1回。
通常samplerを各(agent, channel, tick/window)の唯一の所有者とし、packet作成や再送から再取得しない。
Probeは通常の遠景枠を1回使い、臨時sampleを足さない。回転は最大1回・45度、
元記録鮮度2秒、操作から取得終了まで1.5秒、台帳16件/個体を維持する。

全感覚pendingは既存の最大64frame/個体を共用し、HTTP配送は最大4frame/回。
8Bの視覚専用8件queueを別に残して二重配送しない。Probe許可時の1件予約も共通64件へ含める。
6秒の通常予定数は個体あたり近景24＋聴覚24＋遠景6＝54frame。重複取得でこの上限を水増ししない。
欠落・枠逸失は未取得として記録し、空の完全取得frameを捏造しない。
遅延時のqueue実測最大値と予約数をEvidenceに残す。容量不足は拒否・欠落として扱い、
未ack frameを破棄して試験を通さない。Runtimeの既存有限store上限も拡大しない。

HTTP in_flight / callback mailboxは各1件/個体、配送台帳32件/個体、調停trace256件/個体。
HTTP timeoutは3秒、run終了後のdrainは最大5秒。終了後に新規身体操作や取得をしない。
大きなdtimeや窓の飛越しでは取得できなかった区間を保持し、無制限catch-upしない。
聴覚の検出時姿勢と受信区間を、配送時の身体状態で上書きしない。

## 5. 統合シナリオと完了判定

全感覚・A/B・継続時計・生活・明示Probeを共通構成として、少なくとも以下を実行する。

- 正常再取得とA/B役割交換。片方のProbe中も他方は生活を継続。
- 生活intentと取得枠の競合、回転後の中断と生活復帰。
- callback遅延中の三感覚取得、取得後の身体移動と遅い受付。
- 感覚拡張の意図的拒否と回復、送信見送り、受理後応答消失と同ID再送。
- 新要求後の旧応答再注入、ack集合と身体権限の独立性。
- 完全取得で条件不適合、欠落/上限、姿勢対応失効の結果分類。

同runで複数の故障を重ねる結合ケースも1本以上設け、故障同士をマスクせず、
取得から受付・評価・生活完了までIDで追う。各故障を一度に詰め込むこと自体を目的にしない。
少なくとも正常再取得・生活中断・配送障害回復は実Luantiの全感覚統合runで通す。
比較不能の厳密境界や容量超過を合成試験で補う場合は、実機取得と区別して表へ記載する。
既存OBS-8B/8/7B/7A/6E/4C/遠景と全体試験を回帰し、意図的skipをPASS数に含めない。

10項目すべてのassertionと証拠が揃い、必須実機runと回帰が成功した場合だけ、
**「観測の精度は粗いが、GameAIの後段を研究するには十分な観測基盤v1 COMPLETE」**と宣言する。
失敗・未実施・判定不能が残る項目が一つでもあれば未完了。既存Evidenceの再掲だけで完了にしない。
完了時のcommitとEvidenceを基準として固定し、後段の都合で追加能力が必要なら別の用途契約にする。

## 6. v1完了の条件に含めない能力

精密画像認識、物体認識、音源同定、音声認識、反射・回折の精密音響、匂い、
移動しながらの一般姿勢変換、動的sensor profile、長期永続化、任意ネットワーク障害、
自律注意、対象追跡はv1の必要条件から除外する。用途が具体化したときに追加する観測能力である。
canonical接続やM_B更新もOBS-9で追加しない。
見える対象を増やすことより、何が取得できず、なぜ判断できないかを区別できることを優先する。
