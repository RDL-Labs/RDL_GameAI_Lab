# 味・満腹・消化の小規模実験

[1,000体・10,000体の消化ON/OFF負荷比較](benchmark-report.md)：身体更新だけを測定。10,000体で追加約0.093 ms/シミュレーション秒。世界全体の性能ではない。

既存Julia LWの食事部分へ、opt-inの遅延消化を接続。捕食者や狩猟を追加した実験ではない。

## 単純化

- 食料1個＝栄養20。普通食と肉の栄養・消化速度は同じ。
- 腹の容量は2個。1個を1,800 simulation secondsで消化し、少しずつreserveへ移す。
- 味の基準値は普通食1、肉1.5。今回の個体の仮の好みであり、生物一般の法則ではない。
- 味＝基準値×腹の空き割合×連食による低下×reserveに応じた係数。
- 食べた種類への飽きは0.6増加、上限1。時間とともに指数減衰（時定数7,200秒）。
- reserve上限100を超える栄養はoverflowとして記録。摂食栄養＝消化管残量＋吸収＋overflowを検査。
- 即時の味評価を身体エネルギーやHへ直接加算しない。

腹が満杯なら追加の食事を選ばない。腹の中の将来の回復量を見越す満腹判断はまだ未実装。身体部位・栄養素・ホルモンは扱わない。

## 二つの確認

1. **同条件の食料選択fixture**：通常食と肉を同じ費用・量で提示し、その時点の味評価が高い方を選ぶ。最初は肉、直後は連食効果で通常食、2食後は満腹で停止。学習や狩猟による選択ではなく、評価式の挙動確認。
2. **LW3個体・1日**：同じ保存specで即時回復OFF、遅延消化＋普通食、遅延消化＋肉の3条件。食事種類は試行全体で固定し、既存の食料をその種類とみなす。肉の取得・個別食料在庫・味による探索先選択は未接続。

| 条件 | 摂食数 | 個体Aの最終reserve | 味評価合計（A） |
|---|---:|---:|---:|
| 既存の即時回復 | 3 | 84.198 | 記録なし |
| 遅延消化・普通食 | 4 | 97.549 | 1.497 |
| 遅延消化・肉 | 4 | 97.549 | 2.246 |

遅延条件ではAのみが食べ、4食の栄養80のうち約73.302を吸収、約6.698がoverflow。栄養が同じなので普通食と肉の身体・行動結果は完全一致し、味の記録だけ変化した。

肉の各食の評価は約1.275→0.409→0.300→0.262。満腹度・身体状態・飽きが同時に変わるため、低下全てを飽きだけの効果とはしない。

遅延回復では食事回数が増え、後から余剰が生じた。次は腹の中の栄養をどの程度「すでに満たされつつある」と扱うかが検討点。現時点でより良い行動になったとは主張しない。

## 再実行

```sh
julia --startup-file=no --project=experiments/julia_migration/julia experiments/digestion_taste/run.jl
```

小さな集計をresults.json、大きな結果と各条件のspecをoutputs/digestion-tasteへ保存。生成したspecは共通入口でも実行できる：

```sh
julia run.jl lw outputs/digestion-replay --spec outputs/digestion-taste/meat-spec.json
```

保存specの`config.digestion`は`off`（既定）/`ordinary`/`meat`。専用CLIフラグは追加していない。既存設定を省略した場合とoffは全結果一致。変更前に保存した同じ1日結果とも一致を確認。

単体21項目、選択fixture、OFFの省略時一致、保存済み旧結果一致、普通食/肉の味以外の一致、摂食数整合性、肉条件の再現一致を確認（このPCでは計27項目）。旧結果ファイルがない環境では保存済み旧結果との比較1項目のみ省略。各条件の実行中に既存の食料保存則と追加した栄養収支も検査。

次段階は味の期待を行動選択へつなぎ、兎の捕獲→肉取得→所持→食事へ接続すること。今回まだ「美味しいので兎を狩る」動作は実装していない。
