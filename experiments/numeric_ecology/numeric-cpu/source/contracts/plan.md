## 1. 目的と判断対象

最終目的は、単一関数の最速化ではなく、**「着想 → 変更 → 実行 → 挙動確認」の一巡を短くすること**である。以下を別々に判定する。

| 判断対象 | 確かめたいこと | それだけでは主張しないこと |
|---|---|---|
| 言語・実装適性 | AIがJuliaで実装・検査・修正を一巡できるか | JuliaならRDLを正しく実装できるという一般保証 |
| 同等移植の性能 | 同じ入力・規則で時間とメモリを減らせるか | アルゴリズム変更や観測省略による高速化 |
| 接続の実用性 | Pythonとの受け渡し込みでも有効か | Julia内部の速度だけで全体高速化を宣言すること |
| RDL向け構造の適性 | 関係近傍検索・H・ρを小さな操作として扱えるか | canonical M_BやCore定義の変更・完成 |
| 観察体験 | 継続・切替・失敗後の変化を追いやすいか | 採取数が増えれば面白さも向上したという同一視 |

本書の段階番号、件数、速度目安、候補数は**今回の提案値**であり、既存RDL仕様や実測結果ではない。着手前に契約へ固定し、結果を見て有利に書き換えない。

### 2.2 理論資料から保持すること

T0の `M_B` は特定のBのもとで保持する有限関係拘束構造、`RIB_B` は作用側の有限断面である。Hは差Eの単純な総和ではなく、現在のM_Bで吸収・解消されずに残存する状態である。ρはB内部での区別の細かさであり、検索範囲・浮動小数点のビット数・B変更そのものと同一視しない。[P1–P4]

**「Hが高いと関係検索の範囲を広げる」は、今回試すGameAI-localな応答方針であって、Coreの新しい普遍則ではない。** 既存の局所Hとcanonical H、方法変更とT1の検査・選別・再構成を混同しない。

## 4. 初回範囲：J0〜J2だけで答えを出す

### 4.1 何を作るか

第一候補は、`integrations/lightweight/world.py`の以下の処理。

- `segment_hit(start, end, obj, margin)`
- `ray_hit(start, direction, obj)`
- 固定された複数queryと物体群を処理するバッチ関数

これは「最も重いから」と決め打ちする選択ではない。**境界が小さく、行動規則を変更せず、AIのJulia対応力を検査しやすいから**最初の試作品にする。J0で他の処理が支配的と分かれば、幾何試作は能力検査までとし、全体移植対象を改めて選ぶ。

初版は既存の式・比較条件・query順・物体順を保持する。空間索引、GPU、並列処理、Float32化、fast-math、新しいH規則、動的ρを同時に導入しない。

### 4.2 共通入力と正しさ

Pythonの固定commitから入力fixtureと参照出力を一度生成し、SHA-256を保存する。Julia側で「同じseedだから同じWorld」と仮定しない。World配置と乱数による選択が必要なら、その値または固定された乱数列を共通入力にする。

初回の提案規模は、境界例20件以上と固定生成例1,000件。性能用には実際のバッチ規模と拡大規模を分ける。大規模合成データで速かったことを、実GameAIでの高速化と同一視しない。

| 分類 | 初回に含める検査 |
|---|---|
| 幾何の基本 | hit/miss、背面、円内部始点、零長線分、接線、端点接触、margin |
| 数値境界 | 判別式や距離閾値のちょうど・直前・直後、負座標、許可された座標範囲 |
| 順序 | 同距離hitなど、参照実装の決定順を保持。移植と同時に新しいtie-breakへ変えない |
| データ契約 | 長さ不一致・不正形状・非有限数等の扱いを事前宣言。不正入力を無言で正常値へ置換しない |
| 状態保全 | 入力fixtureのhash不変、再実行の同一性、返却バッファが過去記録を書き換えないこと |
| 本人とWorld | 幾何のWorld真値はWorld側計算にだけ使う。個体側の候補検索へ隠れた座標・物体IDを渡さない |

出力を三層で比べる。

1. **厳密一致:** hit/miss、状態区分、順序、対象の選択、ID、個数、操作権限など。
2. **事前宣言した許容差内:** 距離等の浮動小数点値。初回案はFloat64、距離の `atol=1e-12 World単位 / rtol=1e-12`。実際のスケールと既存portable replay規則を確認してJ0で確定する。
3. **決定境界:** 数値が許容差内でも、hitや選択結果が変わったら同等移植の合格にしない。最初の不一致を切り出す。結果を見た後の丸め追加で隠さない。

不正入力についてPython側に明確な契約がなければ、「同等移植の共通入力域」と「新しいwrapperの検証」を分ける。既存コードの未定義な使い方を勝手に標準へ昇格しない。

### 4.3 AIの扱いやすさも成果に含める

初稿の成功だけでなく、初稿後に追加した境界例またはバッチ仕様の小変更に対応させる。既存テストを削らずに改修できるか、失敗原因を入出力まで追えるか、型不安定・大きなメモリ確保を診断できるかを記録する。

初回は通常の関数・構造体・配列を使う。独自DSL、生成マクロ、型の自動増殖は要求しない。ρは後段の設定データであり、数値が変わるたびに新しい型を作らない。

## 5. 計測を混ぜない

### 5.1 固定する条件

基準commit、実験差分commit、OS/CPU、Python/Juliaの正確な版、依存lock、スレッド数、World入力、個体数、seed、時間profile、観測間隔、movement_inertia、ログmodeをmanifestへ保存する。

開始時は単一スレッド。最初の比較環境は、同一の安定したLinuxホストを想定する。Juliaの版はJ1で公式配布と互換性を確認してパッチ版まで固定する。本書では未確認の最新版番号を指定しない。Project.toml/Manifest.tomlを実際の環境から生成して保持する。[E1]

Juliaは初回コンパイル・読み込みと反復処理を分けて測る。`@code_warntype`等は診断に使い、明示型を増やしただけで性能が上がったとは扱わない。[E2]

### 5.2 指標

| 指標 | 定義・扱い |
|---|---|
| 冷間時間 | 新しいプロセスで起動→最初の有効結果。依存の初回ダウンロードは別記録 |
| 反復カーネル時間 | 読み込み・コンパイル後、固定入力を処理する時間 |
| 接続時間 | 引数整形・コピー・変換・Julia呼出し・戻り値整形を含む |
| 統合時間 | 同じWorld時間を処理する本体の時間と、起動/出力/後処理込みの総時間を両方保存 |
| メモリ | プロセス全体の最大RSSと、カーネルの確保量・GC時間を分ける。異なる計測器の値を無条件に比べない |
| 計算量の代理指標 | 幾何query数、訪問関係数、展開数、詳細評価数、ρ変更数、再観測数 |
| 意味と挙動 | 状態区分・操作列・最初の差分、保存則、Sleep完了/中断、食料取得、帰還、停滞区間 |
| 開発の回転 | 環境復元、局所テスト、小変更の検査を一巡できるか。修正回数と手動介入を記録 |

プロファイラは原因の探索に使い、言語間の速度比較はプロファイラなしで行う。特にPython公式も、プロファイラによる時間をベンチマークへ直接用いないよう注意している。[E3]

ベンチマークは入力生成を測定内/外のどちらに置いたか明示する。状態を更新する試験は毎sampleで元状態に戻す。BenchmarkToolsではsetupと測定本体を分離できるが、setupを除外した数値を接続込みの結果と呼ばない。[E4]

### 5.3 比較組

| 組 | 比較する条件 | 分かること |
|---|---|---|
| P-events / P-off | 同一Python・同一挙動規則でログ条件だけ変更 | テレメトリ系を省いた効果 |
| P-reference / J-equivalent | 固定入力・同一規則・同一出力契約 | 言語とデータ表現を含む同等実装の差 |
| P-batch / P-to-J-batch | 同じ観測一回分を処理、接続を含める | 現実の受け渡し単位で得か |
| P-full / J-opt-in | 同じログmode・同じWorld条件で短区間 | GameAI全体へ戻した場合の差 |
| J-fixed / J-adaptive | 同じJulia環境でR1/R2だけ変更 | 新しい探索・解像度方針の差 |

`Python events`と`Julia off`だけを比較し、差をJuliaへ帰属しない。`off`では操作監査がないため、正しさのrunはevents/fullで別に保持する。最終状態一致だけから、全経路が同じだったと断定しない。[R1]

初回の性能報告は3回以上の独立した測定系列。J3/J4の採用判断は同一ホストで順序を交替した5組以上を提案する。中央値とばらつき・全測定値を保存し、一番良い値だけを採用しない。再実行ごとに出力先を分ける。

### 5.4 仮のGo / No-go目安

以下は達成予測ではなく、今回の意思決定用の提案目安。

- **意味維持:** J2の厳密な区分・選択の不一致0。違反がある間は本線で有効化しない。
- **局所性能:** 代表的バッチの準備後速度が2倍程度以上ならJ3へ進む有力材料。小さな処理だけ速くても本線採用は決めない。
- **接続後・全体性能:** 同じ600秒窓で総時間を20%以上削減（速度比1.25倍以上）できれば局所採用の有力材料。ばらつきに埋もれる場合は未判定。
- **メモリ:** 同一ホストの最大RSSが暫定2倍を超える場合は無条件採用しない。Julia起動分と状態保持増大を分けて判断する。
- **改修性:** 初稿後の変更でも意味契約と過去テストを保ち、クリーン再現できること。速度だけ良くても継続開発が不安定なら保留する。

速くならなかった場合も実験は有効である。対象選び、接続粒度、内部表現、またはアルゴリズムの課題として結果を保存し、全面移植は止める。

補助的な見積りとして、対象部分の時間比率をp、その部分の速度比をsとすれば、接続費用を除いた全体速度比は概ね `1 / ((1-p) + p/s)` と考えられる。これは実測に代わる保証ではなく、支配的でない処理の高速化を過大評価しないための目安。

## 6. J3/J4：接続と復帰の契約

JuliaCallはPythonからJuliaを呼べる候補であり、依存環境と変換規則が用意されている。[E5] ただし採用はJ2後。初回J2は保存fixtureによる独立実行でよい。

接続する場合は、一つの常駐Julia実行系へ「現在観測一回分のquery群」をまとめて渡す。レイ一本ごとに起動・言語間往復を行わない。将来のtickを一括計算して割込みを飛ばすこともしない。

データ形式変換は境界で行い、Julia内でPythonオブジェクトの辞書を一件ずつ操作する実装にしない。最初は所有権が明確なsnapshotを使う。ゼロコピーを導入するなら、共有バッファの後続更新が過去観測や比較窓を変えない検査を追加する。

backend名は次を**新設案**とする。現在存在するCLIとして扱わない。

- `python`: 既定。Julia未導入でも既存経路が動く。
- `julia-shadow`: Python結果だけを採用。Juliaは同一snapshotに対して比較出力のみ。
- `julia`: 明示opt-inで結果を採用。起動不能・不一致は明示失敗として記録し、性能実験中に無言でPythonへ切り替えない。

World・身体・在庫の書換権限は既存側一つに保つ。shadowの両計算から身体結果を二重発行しない。無効化すればPythonへ戻れることを検査する。

J4ではまず600 World秒の対応比較を行う。夜間を含まない短窓だけでSleep完了を検証したとは言わない。終了前休息・危険割込みは独立した小さな境界fixtureで確認し、最終的に1日通しで接続を確認する。既存checkpointが完全な中途再開に使えるとは仮定しない。再開試験を作るなら、World・身体・記憶・乱数・pending操作と期限を含む復元同値性を別途確認する。

## 7. R1/R2：RDL向け新構造は別の実験にする

### 7.1 関係範囲・候補数・ρを別々に持つ

| 操作項目 | 意味 | 初回の扱い |
|---|---|---|
| 関係の起点 | 現在の目的・使用中の方法・本人の直近経験 | 許可された本人側データだけ |
| 検索範囲 | 起点からどこまで既存関係を辿るか | 局所Hに応じて有限段階を拡張 |
| 詳細評価数K | 呼び出した中で細かく評価する件数 | 例としてK=4、探索とは別の予算 |
| ρ | 同じ範囲・問いの内部を区別する細かさ | coarse / fineを定義し、必要局所のみ変更 |
| 監視・割込み | 危険・身体・期限・目的変化の検出 | 候補top-kの外に置き、抑制しない |

`H_local/θ_local`を拡張圧力の補助値として使うなら、その局所モデル内で単位と意味が対応する場合に限る。異なる目的のHを無条件に比較・加算しない。検索拡張の段階値をcanonicalなθの代用品にしない。[P2]

検索は隣接関係・目的別索引等から開始し、安価な粗評価で候補を呼ぶ。全候補を詳細評価した後にtop-kだけ残す実装は、R1の計算節約として不合格。索引の構築・更新・キャッシュ無効化の費用も計測する。

高Hでも無制限に全展開しない。探索済み範囲を保持し、新しい証拠・関係revision・状態変化で必要部分を再検査する。候補が見つからない場合は、Hを0にせず未解決と許された待機・再観測等を残す。強い関係だけで固定化しないよう、近傍不成立時の追加探索を検査する。

### 7.2 ρの契約

ρ上昇には次のどれかを必ず記録する。

1. 既に合法的に取得・保存していた詳細データを再処理した。
2. 新しい有限観測を要求・取得した。
3. 既存証拠のもとで仮説を細分化した。これは新しい観測事実ではない。

粗い記録だけから詳細なWorld真値を復元しない。遮蔽・未観測・比較不能を高ρで無言に埋めない。高ρを下げても未解消Hを自動消去しない。低ρと高ρのF/F′は、明示した共通射影または新しい比較窓で扱う。比較契約がないならdeferする。[P2, P4]

初回R2は空間/特徴の細分化に限定し、観測時間間隔・World tick・Hの評価頻度は変えない。時間的ρは別の検証対象として後段に残す。

### 7.3 同じJulia内での2×2比較

| 条件 | 検索範囲 | ρ | 分離する効果 |
|---|---|---|---|
| R00 | 固定された有限全候補集合 | 固定fine | 小規模実験の比較対照 |
| R10 | Hに応じた関係近傍拡張 | 固定fine | 検索方針の効果 |
| R01 | 同じ有限全候補集合 | 適応的 | ρ方針の効果 |
| R11 | Hに応じた関係近傍拡張 | 適応的 | 両者の組合せ |

R00の「全候補」は、この実験に用意した本人側の有限集合を意味し、世界全体やξの回収を意味しない。四条件の比較は新しい設計の試験であり、J系列の同等移植と違って行動差が出てもよい。その差を品質・費用・失敗原因として残す。

最初のscenarioは、近傍で解決／近傍に解なし・外に代替あり／粗観測で曖昧・詳細で分離／遮蔽で詳細化無効／候補探索中の危険割込み／候補があっても身体不能、の6種を提案する。

## 8. 意味維持の共通境界

以下は速度や見栄えと交換しない。

- World真値、個体が取得した有限観測、本人のM_B・局所モデル、実験者ログを分ける。
- `unknown / not_observed / incomparable`を、0・不存在・安全・失敗に置き換えない。
- Eの比較は同じ更新前M_Bと宣言した比較条件へ束縛する。HをEの総和や検索回数へ再定義しない。[P2]
- H/θによる既存候補の選択変更を、canonical T1採用の完了と呼ばない。[P3]
- 再送で経験・成功支持・H・休息量・在庫操作を重複加算しない。
- 手段の不成立、身体不能、危険割込み、未実行を区別し、待機成功で元の移動Hを解消しない。
- 実在庫、実身体結果、実休息に基づく収支を保持する。完了と学習材料十分を分ける。
- モデル強度、H、ρ、検索予算、計算費用を別の変数として追えるようにする。

初版で全RDL層をJuliaへ写し取る必要はない。選んだ小さな境界で上記契約を守る。

## 10. 現行コードで使えるJ0コマンド例

以下は確認HEADのCLIに基づくLinux向け例。リポルートで実行する。`python`が基準環境を指すことと、出力先が未作成であることを確認する。既存作業をreset/cleanしない。[R3]

```bash
# テレメトリあり：監査と挙動比較の基準
PYTHONHASHSEED=0 RDL_LW_TIME_PROFILE=human_scale_v1 \
python -m integrations.lightweight.long_ground_campaign \
  --days 1 --seconds 180 --observation-us 1000000 \
  --movement-inertia --log-mode events \
  --output outputs/julia_migration/baseline-events-01

# テレメトリなし：性能の切り分け。操作監査済みとは扱わない
PYTHONHASHSEED=0 RDL_LW_TIME_PROFILE=human_scale_v1 \
python -m integrations.lightweight.long_ground_campaign \
  --days 1 --seconds 180 --observation-us 1000000 \
  --movement-inertia --log-mode off \
  --output outputs/julia_migration/baseline-off-01
```

プロファイルでは監督側ではなくworkerを直接指定する。この入口は出力先を自動作成しないため、専用ディレクトリを先に作る。これは原因探索用であり速度比の測定には使わない。[R3, E3]

```bash
mkdir -p outputs/julia_migration/profile-01
PYTHONHASHSEED=0 RDL_LW_TIME_PROFILE=human_scale_v1 \
python -m cProfile \
  -o outputs/julia_migration/profile-01/profile.pstats \
  -m integrations.lightweight.long_ground_campaign \
  --worker --days 1 --seconds 180 --observation-us 1000000 \
  --movement-inertia --log-mode off \
  --output outputs/julia_migration/profile-01
```

上の180秒は**World内の試験区間**であり、実作業時間の見積りではない。初回は1日・複数日・CIの長時間runを追加しない。
