# H解決量に依存する報酬（2026-10-22）

共通BasicLoopの目的達成時に `R = max(0, 解決前の親H - 解決後の親H)` を与える。現在のBool型の目的判定では成功でHが0になるのでRは解決前のHそのもの。失敗・未確認・単なる移動では報酬0。H=0での達成も0。部分解決の評価は未導入。既存H上限32は維持する。

報酬は同じ目的の実行履歴にある異なる候補（最大32件）へ等分する。LWは実行済みかつ移動または局所成果のある操作を候補履歴に記録する。最後の達成操作も含む。繰り返し回数では重複加点しない。削除済み候補を除いて総報酬量を保存し、達成後は履歴を空にする。同じ結果の再送は二重加点しない。

各候補の累積報酬rewardを保存し、確率選択点を `priority + log1p(reward) - method_H_penalty` とする。成功した経路の報酬が高いほど次回選ばれやすい。親Hによる温度調整は維持する。既存のroute supportは成功証拠の件数として保持し、新しい報酬量と区別する。新しい報酬は個体・目的別のMethodNodeに保持され、経路候補もそのIDで受け取る。

この分配は実行履歴による暫定的な貢献推定であり、因果的な経路学習ではない。汎用step候補への報酬は場所別に分かれていない。自己誘発した未解決と外部由来の困難を区別する仕組みもないため、遠回りの誘因は今後の実験で確認する必要がある。慣性優遇・方向固定は復活させていない。

検証: h_reward_checks.jl 19件PASS、確率選択・経路学習116件PASS。高H/低Hの報酬差、未解決・未知・H0で無報酬、分配総量、選択確率への反映、再送、履歴上限、重複、削除済み候補を検証。

3体・1日のLW実行も正常終了（seed 20261005、コンパイル込み約19秒）。長期の効率・遠回り傾向は未検証。

## 失敗は成功報酬と別に記録

失敗時に累積成功報酬を減算しない。候補の判定がfalseかつ親目的もfalseの場合のみ、確定失敗としてfailure_count、failure_H_totalを更新する。直近32件のイベントには候補・評価質問・結果source・親Hの前後・failed・failure_Hを保持する。目的はループのgoalに保持する。結果不明や、局所成果はあるが親目的は継続中の場合を確定失敗と混同しない。H0の失敗も回数として残す。同じ結果の再送で重複記録しない。

失敗した候補は未配分の貢献履歴から除く。成功報酬の記憶は保存する。既存の一時的な候補Hペナルティは維持するが、蓄積した失敗履歴から持続的な反発ポテンシャルを作る接続は未実装。勾配の空間的な近傍関係も現時点では定義していない。

追加検証: 失敗履歴と成功保持14件、H報酬19件、既存確率選択116件、計149件PASS。

追記: 失敗履歴の候補反発を接続済み。現在の方式と制約は[failure_repulsion_report.md](failure_repulsion_report.md)を参照。
